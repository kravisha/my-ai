MY AI — PRE-ALPHA COO STARTUP, OBSERVABILITY, AND PERSISTENCE SPECIFICATION
Version: Pre-Alpha Milestone 1
Date: 2026-08-25

1. PURPOSE

The purpose of this milestone is to implement enough of the system that the operator can:

1. Start the application.
2. See a login screen.
3. Authenticate using the Server Superuser credentials.
4. Cause the COO process to start automatically after successful login.
5. Observe the system starting up in real time.
6. Observe departments, engines, agents, work queues, idle states, and major state transitions.
7. Query the COO through a chat interface.
8. Shut down the system cleanly while persisting long-lived agent and system state.
9. Restart the system and restore persisted agents and relevant state.

The goal of this milestone is NOT feature completeness.

The goal is an observable, persistent, end-to-end vertical slice of the system that works.

Pre-alpha success means:
"Something real works from startup through orchestration, status reporting, persistence, restart, and continued operation."


2. CURRENT SYSTEM STAGE

The system must have a persisted lifecycle stage.

Initial stage:
PRE_ALPHA

The lifecycle stage must not exist only in memory.

It must be persisted so that the COO can read it at startup and alter behavior based on the current stage.

Example stages for future use:
- PRE_ALPHA
- ALPHA
- BETA
- PRODUCTION

For this milestone, PRE_ALPHA is the required active stage.

The COO must know at startup:
- current lifecycle stage
- current implemented asset classes
- current development focus
- currently available engines/departments
- persisted system/agent state


3. LOGIN AND COO PROCESS CREATION

3.1 Login screen

The application begins with a login screen.

For development, authentication will use Server Superuser credentials configured externally.

Required configuration keys:

SERVER_SUPERUSER_ID
SERVER_SUPERUSER_PASSWORD

These credentials may initially be stored in the existing .env development configuration.

The .env file must never be committed to Git.

3.2 Authentication abstraction

Do not spread direct .env access throughout the codebase.

Create an authentication/configuration abstraction so that later migration from .env credentials to database-backed or production-grade authentication does not require rewriting the rest of the application.

3.3 COO creation

The COO process must NOT start before successful login.

On successful Server Superuser authentication:

1. Create or restore the COO process.
2. Load lifecycle stage.
3. Load persisted system state.
4. Initialize the COO interface.
5. Begin the startup sequence.
6. Begin publishing visible status events.

The operator-facing system begins with the COO, not with a generic "server interface."


4. COO USER INTERFACE

The primary logged-in interface is the COO interface.

It is a control panel for the system.

4.1 Main layout

The interface must contain at least:

A. Large live status/activity area
B. Status filtering controls
C. COO chat/command interface

4.2 Live status area

A large scrolling text/status area should occupy a substantial portion of the interface, approximately the upper one-third or more of the usable screen.

It continuously publishes operational updates.

Examples:

[10:00:01] COO starting
[10:00:01] Lifecycle stage loaded: PRE_ALPHA
[10:00:02] Metadata Engine starting
[10:00:02] Metadata tables verified
[10:00:02] Metadata Engine ready; entering idle state
[10:00:03] Reference Data Engine starting
[10:00:04] Reference data available
[10:00:04] Simulation Engine starting
[10:00:05] Education Department starting
[10:00:05] Education Department waiting for minimum usable data
[10:00:07] Curriculum item generated
[10:00:07] Training agent assigned work
[10:00:08] Explorer training task started
[10:00:09] Speculator waiting for work
[10:00:10] Analyst trainer evaluating output

The feed should behave like continuous operational narration.

4.3 Status event schema

Every status event should include, where applicable:

- timestamp
- event_id
- lifecycle_stage
- source_department
- source_engine
- source_agent
- event_type
- severity
- status
- human-readable message
- task_id if relevant
- correlation_id / trace_id if relevant

Suggested severity values:
- DEBUG
- INFO
- WARNING
- ERROR
- CRITICAL

Suggested status values:
- STARTING
- RUNNING
- WAITING
- IDLE
- READY
- COMPLETED
- FAILED
- STOPPING
- STOPPED
- RESTORED

4.4 Filters

The status display must be filterable.

At minimum allow:
- All
- COO
- Metadata Engine
- Reference Data Engine
- Simulation Engine
- Education Department
- Training
- Explorer
- Speculator
- Analyst
- Trainers
- Errors/Warnings

Architecture should allow new departments to appear without rewriting the UI.

4.5 Queryability

Status must not only be displayed transiently.

The operator must be able to query the current state through the COO.

Examples:

"What stage are we in?"
"What is the Reference Data Engine doing?"
"Which departments are idle?"
"What agents are running?"
"What failed during startup?"
"What curriculum is ready?"
"What is waiting for work?"
"Show me recent Simulation Engine activity."

The COO should answer using actual system state/status data rather than inventing an answer.

4.6 Status history

Persist enough event/status history to support:
- recent history queries
- debugging
- restart continuity
- examination of what occurred before shutdown/failure

A full enterprise event store is not required for pre-alpha.

A simple durable implementation is sufficient.


5. COO STARTUP SEQUENCE

After successful login:

STEP 1
Create or restore COO.

STEP 2
Load persisted lifecycle stage.

STEP 3
Load boot configuration.

STEP 4
Start Metadata Engine.

STEP 5
Metadata Engine verifies/creates required global metadata structures.

STEP 6
Metadata Engine reports METADATA_READY.

STEP 7
After metadata readiness, start Reference Data Engine.

STEP 8
As soon as minimum usable reference data exists, allow dependent work to begin.

STEP 9
Start Simulation Engine when its minimum required inputs are available.

STEP 10
As soon as some usable reference and simulation data exist, Education Department may begin curriculum generation.

STEP 11
As soon as curriculum items become available, they may be passed to training agents.

STEP 12
Training agents begin assigning work to domain agents such as Explorer and Speculator.

STEP 13
Outputs may flow to Analyst.

STEP 14
Analyst trainers evaluate Analyst work and continue training cycles.

The architecture should support overlap and parallelism.

Do NOT require the entire dataset or entire curriculum to finish before downstream work starts.

The system should become productive as soon as minimum usable inputs exist.


6. PRE-ALPHA OPERATING PRINCIPLE

During PRE_ALPHA, correctness matters, but perfection is not required.

Primary objective:
MAKE THE COMPLETE LOOP WORK.

Reference data does not need to contain the entire securities universe.

Simulation data does not need to be market-perfect.

Curriculum does not need to be exhaustive.

Agents do not need to be fully trained.

What must work:
- startup
- orchestration
- data availability
- simulation generation
- curriculum generation
- task assignment
- training loop
- status reporting
- persistence
- shutdown
- restart
- restoration

The system should favor a functioning small universe over a non-functioning perfect universe.


7. PARALLEL PIPELINE BEHAVIOR

The pipeline is not strictly sequential.

Example:

Reference Data Engine produces a small usable set.
-> Simulation Engine begins producing data.

As soon as reference + simulation data cross a minimum usable threshold:
-> Education Department begins generating curriculum.

As soon as one curriculum item is ready:
-> Training can begin.

Training must not wait for all curriculum to exist.

Education must not wait for the entire simulated universe.

Simulation must not wait for exhaustive reference data.

Each component should publish:
- readiness
- minimum-input threshold reached
- work started
- work completed
- waiting/idle status


8. PERSISTENCE REQUIREMENT

Persistence is mandatory from this milestone onward.

8.1 Principle

Long-lived agents must survive system shutdown and restart logically.

Do not treat every restart as creation of a brand-new population.

8.2 On shutdown

COO initiates coordinated shutdown.

Required sequence:

1. COO publishes SYSTEM_STOPPING.
2. Stop assigning new work.
3. Allow active work to reach a safe checkpoint where practical.
4. Request every persistent agent to serialize its state.
5. Persist system-level state.
6. Persist agent registry.
7. Persist agent state.
8. Persist relevant task/work state.
9. Confirm persistence success.
10. Shut down components in controlled order.
11. Publish final shutdown result.

If an agent cannot persist, the shutdown log must clearly identify the failure.

8.3 On restart

After authentication:

1. COO starts/restores.
2. Load lifecycle state.
3. Load agent registry.
4. Restore persisted agents.
5. Restore their names and stable identities.
6. Restore relevant state/checkpoints.
7. Resume or reconcile outstanding work according to safe restart rules.
8. Continue status publication.

8.4 Storage implementation

For pre-alpha, file-backed persistence is acceptable.

JSON files, structured local files, or SQLite may be used depending on existing architecture.

The persistence API should be abstracted so storage can later move to another database without rewriting agents.

8.5 Agent persistence minimum fields

Each persistent agent should have at least:

- stable_agent_id
- assigned_name
- agent_type
- department
- role
- lifecycle_status
- created_at
- last_updated_at
- last_checkpoint_at
- current_task_id if any
- training state/progress as applicable
- relevant memory/state references
- version/schema_version

Never reassign a persisted agent's name on restart.


9. AGENT CREATION AND NAMING

Agents are assigned human-style names from the global Agent Names pool.

A single name is sufficient.
First/last name support may be added later.

When a new persistent agent is created:

1. Atomically reserve one unused name from Agent Names.
2. Assign it to the agent.
3. Persist the agent immediately with that name.
4. Remove or mark that name unavailable in the global available-name pool.
5. Never return it to the available pool merely because the process restarts.

The operation must be safe against duplicate assignment if multiple agents are being created concurrently.

A name becomes part of the agent's persistent identity.


10. MINIMUM DEPARTMENTS / ENGINES TO OBSERVE

The first milestone should visibly support startup/state for at least:

- COO
- Metadata Engine
- Reference Data Engine
- Simulation Engine
- Education Department
- Training subsystem
- Explorer
- Speculator
- Analyst
- relevant trainers

Not all need full production behavior.

Some may initially:
- initialize
- report readiness
- report waiting for work
- perform minimal work
- idle

It is important that the COO visibly reports those states.


11. COO CHAT

The bottom portion of the interface must provide a chat/command interface.

The operator can type natural-language queries or commands to the COO.

Initial supported intents may be narrow.

At minimum:

- current system stage
- current system health
- department status
- engine status
- agent status
- recent errors
- current/queued work
- startup progress
- persisted/restored agents

If the requested action is not implemented, the COO should say so explicitly rather than pretend it executed the command.

The chat response itself should also be observable as a system interaction/event where useful.


12. FAILURE HANDLING

Startup must be observable even when something fails.

Example:

Metadata Engine failed
-> COO displays failure
-> dependent engines must not falsely report successful startup

Reference Data Engine has insufficient data
-> Simulation may report WAITING_FOR_REFERENCE_DATA

Education Department has no usable simulation data
-> report WAITING_FOR_MINIMUM_DATA

A failed component should not silently disappear.

The COO must make blocked dependencies clear.


13. HEALTH AND HEARTBEATS

Components should periodically report health to the COO or central status mechanism.

Pre-alpha can use lightweight heartbeat/status updates.

Examples:
- healthy
- busy
- idle
- waiting
- degraded
- failed

Avoid excessive high-frequency logging.

The objective is useful observability, not log flooding.


14. DEFINITION OF DONE

This milestone is done when a developer can:

1. Launch the application.
2. See login.
3. Authenticate with Server Superuser credentials.
4. Automatically enter the COO interface.
5. See lifecycle stage PRE_ALPHA.
6. See Metadata Engine startup and completion.
7. See Reference Data Engine startup.
8. See Simulation/Education/training-related components start or wait visibly.
9. Filter the live feed by department/component.
10. Ask the COO for system status and receive state-grounded answers.
11. Create or restore named agents.
12. Observe agent activity or waiting state.
13. Shut down cleanly.
14. Confirm agents/system state were persisted.
15. Restart.
16. Confirm the same persistent agents are restored with the same identities/names.
17. Continue operation without rebuilding the whole world from scratch.

The key acceptance statement:

"The operator can start the system, log in, watch the COO bring the system to life, understand what every major component is doing, shut it down safely, restart it, and observe the same persistent system continue."
