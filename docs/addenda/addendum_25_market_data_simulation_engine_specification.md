SPECIFICATION 02 — MARKET DATA SIMULATION ENGINE

Project Jarvis / My AI Status: Day Zero / Pre-Alpha Foundational
Specification Dependency: Specification 01 — Reference Data Engine

1. Purpose

The Market Data Simulation Engine creates a controlled synthetic market
world in which the organization can train, test, evaluate, and improve
its agents before relying on historical or live market data.

The first mission is intentionally narrow:

PUT-CALL PARITY ARBITRAGE.

The simulator must create the market conditions, volatility/skew
structures, option chains, pricing relationships, and synchronized
information signals necessary for agents to discover and investigate
put-call parity opportunities.

The simulator is not merely a random price generator.

It is a scenario and training-world generator.

2. Activation Rule

The Market Data Simulation Engine starts only when the user selects:

RUN MODE = SIMULATION

from the mission-control interface.

If Historical or Live is selected, this engine remains inactive unless
explicitly invoked for another permitted purpose.

The COO owns orchestration.

The user chooses the mission.

The COO starts the appropriate engines.

3. Dependency on Reference Data

The Simulation Engine must not invent its own security identities.

Before starting, it requires a READY result from the Reference Data
Engine for the Current Focus.

Every simulated stock, option, contract, signal, post, event, and
relationship must use canonical security identifiers supplied by the
Security Master.

If required reference data is unavailable, simulation remains blocked.

4. Mission-Control Interface

The dashboard shall allow the user to configure a simulation mission.

Initial controls include:

Run Mode

-   Simulation
-   Historical
-   Live

Only Simulation activates this engine.

Asset Classes

The user can select the asset classes participating in the run.

Initial scope:

-   Stocks
-   Stock Options

Additional asset classes can be added later.

Strategy

Strategy is selected from an extensible dropdown.

Initial strategy:

-   Put-Call Parity Arbitrage

The interface must be designed so additional strategies can be added
without redesigning the mission system.

5. Initial Mission

For Version 1, the Simulation Engine’s primary mission is:

Generate realistic market and information conditions containing
controlled option-pricing structures, volatility skew, and deliberate
put-call parity opportunities so that Explorer and Speculator agents can
identify securities worth investigation and pass useful candidates
downstream.

6. Simulation Configuration

A simulation mission should be represented by a structured configuration
containing at least:

-   mission ID
-   run mode
-   selected strategy
-   selected asset classes
-   selected Current Focus universe
-   simulation start/end horizon
-   random seed where reproducibility is required
-   market regime
-   liquidity assumptions
-   volatility assumptions
-   opportunity frequency
-   opportunity magnitude
-   opportunity duration
-   information/noise configuration
-   expected outcomes
-   evaluation targets

The exact fields can evolve.

The important rule is that a simulation is reproducible and auditable
when required.

7. Market World Generation

The engine shall generate sufficient synthetic market data for the
selected strategy.

For stocks and stock options, this may include:

-   underlying prices
-   bid/ask quotes
-   trade prices
-   volumes
-   liquidity conditions
-   option strikes
-   expirations
-   call quotes
-   put quotes
-   implied volatility
-   volatility skew
-   volatility term structure
-   interest-rate/carry assumptions
-   dividend assumptions where applicable
-   timestamps
-   market sessions
-   spread behavior
-   controlled quote noise

Data should be internally coherent except where a deliberate scenario
introduces a controlled anomaly.

8. Skew Generator

The Simulation Engine shall contain a configurable Skew Generator.

Its purpose is to create realistic and deliberately varied volatility
structures.

It should support scenarios such as:

-   flat volatility
-   normal downside put skew
-   call-heavy skew
-   steep skew
-   shallow skew
-   changing skew
-   localized strike distortions
-   term-structure changes
-   event-driven volatility changes

The Skew Generator must be configurable so agents are exposed to more
than one market shape.

9. Put-Call Parity Opportunity Generator

The engine shall explicitly support controlled put-call parity
scenarios.

For the same underlying, strike, and expiration, the simulator should
normally generate prices consistent with the configured pricing model
and carry assumptions.

Selected scenarios shall deliberately introduce deviations.

The Opportunity Generator should control:

-   affected security
-   affected option pair
-   strike
-   expiration
-   deviation direction
-   deviation magnitude
-   duration
-   liquidity
-   bid/ask spreads
-   transaction-cost assumptions
-   stock borrow assumptions where relevant
-   carry assumptions
-   whether the apparent opportunity is genuine or a trap caused by
    market frictions

This allows agents to learn the difference between:

-   true opportunity
-   apparent opportunity
-   noise
-   stale quote
-   spread artifact
-   liquidity artifact
-   carry/dividend effect
-   borrow-cost effect

10. Explorer Output

The Explorer must receive the simulation as ordinary structured MARKET
DATA.

The Explorer should not need to know that the source is simulated.

The simulation interface presented to Explorer should resemble the
interface that will later serve historical or live market data.

Explorer receives, as appropriate:

-   underlying quotes
-   option chains
-   bid/ask data
-   implied volatility
-   skew
-   term structure
-   identifiers
-   timestamps
-   liquidity information
-   other strategy-required structured fields

Explorer’s job is to discover interesting structures and opportunities.

11. Speculator Output

The Speculator receives a different representation of the same simulated
world.

For Version 1, the simulator shall be capable of producing synthetic
Reddit-style chatter associated with specific securities and option
contracts.

Examples of simulated information may include:

-   unusual interest in a stock
-   discussion of an option strike
-   claims of unusual options activity
-   excitement
-   skepticism
-   rumors
-   conflicting opinions
-   incorrect claims
-   noisy repetition
-   low-quality chatter
-   occasional useful observations

This information is synthetic training data.

It must not be represented internally as genuine Reddit content.

12. Synchronized Reality

Explorer market data and Speculator chatter must refer to the same
simulated world.

If the simulator creates an opportunity in Security X, related synthetic
chatter can also reference Security X.

All references must resolve through canonical identifiers.

The simulator must be able to know the ground truth even when individual
agents do not.

This creates controlled partial information:

-   Explorer sees market structure.
-   Speculator sees chatter/noise.
-   Neither needs privileged access to the simulator’s answer key.
-   Evaluation retains the ground truth.

13. Opportunity Signaling Philosophy

The simulator must not simply tell agents:

“Here is the arbitrage.”

It creates conditions from which agents are expected to discover the
opportunity.

Signals may be obvious in early training and progressively subtler
later.

The training system should therefore support difficulty levels.

14. Agent Collaboration Goal

Explorer and Speculator are expected to collaborate and produce
candidates worth deeper investigation.

Their effective output is:

“This security / structure is worth investigating.”

The candidate is passed to the Analyst.

The Analyst performs deeper validation.

The simulator provides enough underlying truth for the eventual result
to be evaluated.

15. Expected Outcome / Ground Truth

Every purposeful simulation scenario must have machine-readable ground
truth.

Ground truth should record:

-   what scenario was generated
-   which securities were involved
-   whether an opportunity existed
-   what type of opportunity existed
-   expected discovery path
-   expected relevant observations
-   expected strategy behavior
-   expected result or acceptable result range

Agents should not automatically receive this ground truth.

It is primarily for evaluation and training.

16. Evaluation Loop

After agents process the simulated scenario, the Evaluator compares
actual behavior against expected behavior.

Possible results include:

-   PASS
-   PARTIAL PASS
-   FAIL
-   INCONCLUSIVE

The Evaluator should identify whether:

-   Explorer detected the relevant structure
-   Speculator detected useful information
-   collaboration occurred where required
-   the correct security was identified
-   the Analyst investigated the correct thesis
-   the strategy logic was actually exercised
-   the final conclusion was reasonable
-   important false positives were rejected

17. Completion Loop

A simulation is not complete merely because synthetic data was
generated.

The full completion loop is:

Mission Configuration → Reference Data READY → Simulation Engine starts
→ Market World generated → Skew / opportunity scenarios generated →
Explorer receives market data → Speculator receives synchronized
synthetic chatter → Explorer + Speculator identify candidate → Analyst
investigates → outcome produced → Evaluator compares outcome with ground
truth → PASS / PARTIAL / FAIL / INCONCLUSIVE → diagnosis →
training/correction where required → rerun/retry → completion
certification.

18. Strategy-Coverage Requirement

The system must verify that the selected strategy was actually exercised
during the run.

For Version 1:

Selected Strategy = Put-Call Parity Arbitrage.

A run that never presents the agents with a meaningful opportunity to
exercise the selected strategy cannot be considered a successful
strategy-training run.

If the intended strategy was not exercised:

-   flag the run;
-   identify why;
-   adjust scenario generation if required;
-   restart or schedule a retry.

19. Training and Correction

When evaluation fails, the system should distinguish among causes such
as:

-   bad simulated data
-   insufficient signal
-   excessive noise
-   Explorer failure
-   Speculator failure
-   collaboration failure
-   Analyst failure
-   strategy implementation failure
-   identifier/mapping failure
-   interface failure
-   evaluation-rule failure

The appropriate component is then corrected or trained.

The simulation can subsequently be rerun.

20. Reproducibility

Important failed or benchmark scenarios should be reproducible.

The engine should therefore support deterministic random seeds and
stored scenario configurations.

A developer or evaluator should be able to rerun the same world and
determine whether a correction fixed the problem.

21. Scenario Diversity

The simulator must avoid teaching agents that every unusual pattern is
profitable.

Training scenarios should eventually include:

-   genuine parity opportunities
-   no opportunity
-   apparent opportunity erased by spread
-   apparent opportunity erased by carry
-   apparent opportunity erased by dividends
-   borrow-cost complications
-   stale quotes
-   illiquid contracts
-   sudden volatility changes
-   false social chatter
-   useful social chatter
-   contradictory signals
-   normal markets with nothing interesting

The objective is discovery and discrimination, not pattern memorization.

22. Dashboard Visibility

The operations dashboard should display the simulation’s progress
without requiring terminal logs.

Suggested states:

-   NOT_STARTED
-   WAITING_FOR_REFERENCE_DATA
-   CONFIGURING
-   GENERATING_MARKET
-   GENERATING_OPTIONS
-   GENERATING_SKEW
-   INJECTING_OPPORTUNITIES
-   GENERATING_INFORMATION_NOISE
-   READY
-   AGENTS_RUNNING
-   EVALUATING
-   RETRY_REQUIRED
-   COMPLETED
-   FAILED

Useful metrics include:

-   assets simulated
-   option contracts generated
-   scenarios generated
-   parity opportunities injected
-   skew scenarios generated
-   chatter items generated
-   agents completed
-   opportunities detected
-   opportunities missed
-   false positives
-   evaluation pass rate
-   retry count

23. Failure Behavior

The Simulation Engine must fail visibly and safely.

If it cannot produce valid data for the selected mission:

-   it must not report READY;
-   dependent agents remain blocked where appropriate;
-   the dashboard displays the failure;
-   diagnostics identify the failed component;
-   retry is supported.

24. Data Retention

Simulation data is temporary by nature.

The system may discard simulation datasets after their
training/evaluation purpose is complete.

However, sufficient information should be retained for:

-   audit
-   failed-run diagnosis
-   reproducibility
-   benchmark scenarios
-   evaluation evidence

Retention policy can be tuned later because storage cost matters.

25. Testing Requirements

Automated tests should include:

-   configuration validation
-   Reference Data dependency tests
-   canonical-identifier tests
-   stock-data generation tests
-   option-chain generation tests
-   skew-generation tests
-   parity-consistency tests
-   intentional parity-violation tests
-   bid/ask coherence tests
-   reproducibility tests
-   synthetic-chatter synchronization tests
-   ground-truth isolation tests
-   strategy-coverage tests
-   completion-loop tests
-   failure/retry tests
-   dashboard event tests
-   integration tests

26. Initial Acceptance Criteria

Version 1 is acceptable when it can:

1.  Remain inactive unless Simulation is selected.
2.  Receive selected asset classes from the mission interface.
3.  Receive Put-Call Parity Arbitrage as the selected strategy.
4.  Wait for Reference Data readiness.
5.  Use canonical assets from the Security Master.
6.  Generate coherent stock market data.
7.  Generate coherent listed-option chains.
8.  Generate configurable volatility surfaces and skew.
9.  Generate deliberate put-call parity scenarios.
10. Generate both genuine and false/apparent opportunities.
11. Feed Explorer through the normal market-data interface.
12. Generate synchronized synthetic Reddit-style chatter for Speculator.
13. Ensure all signals reference correct canonical securities.
14. Store hidden ground truth for evaluation.
15. Allow Explorer and Speculator to produce investigation candidates.
16. Support Analyst investigation.
17. Support Evaluator comparison against expected behavior.
18. Verify that the selected strategy was actually exercised.
19. Diagnose failures sufficiently to identify the responsible stage.
20. Retry or rerun after correction.
21. Reproduce important scenarios.
22. Display progress and status on the dashboard.
23. Reach an explicit COMPLETED state only after the full evaluation
    loop finishes.

27. Architectural Boundary

The Market Data Simulation Engine owns the synthetic training world.

It does not own:

-   canonical reference identity
-   organizational lifecycle policy
-   Explorer reasoning
-   Speculator reasoning
-   Analyst conclusions
-   judicial/governance functions
-   live market feeds
-   historical-market-data acquisition

Those remain separate components.

28. Foundational Principle

The simulator creates reality for the training run.

The agents should experience that reality through the same kinds of
interfaces they will use later.

The simulator knows the answer.

The agents must discover it.

The Evaluator determines whether they did.

That separation is the foundation of the training loop.
