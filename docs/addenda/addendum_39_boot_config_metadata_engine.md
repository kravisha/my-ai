MY AI — BOOT CONFIGURATION AND METADATA ENGINE SPECIFICATION
Version: Pre-Alpha Milestone 1
Date: 2026-08-25

1. PURPOSE

This document specifies:
- boot configuration
- development authentication configuration
- initial asset-class configuration
- Metadata Engine startup behavior
- the four required global metadata datasets/tables
- current pre-alpha implementation focus

The Metadata Engine is part of the system startup process.


2. CONFIGURATION SEPARATION

Use two categories of configuration.

A. .env
Use for secrets and environment-specific values.

Examples:
SERVER_SUPERUSER_ID
SERVER_SUPERUSER_PASSWORD
GATEWAY_SUPERUSER_ID
GATEWAY_SUPERUSER_PASSWORD
API keys
environment-specific secrets

B. Boot configuration file
Use for non-secret system boot settings.

Recommended names:
boot_config.json
or
boot_config.yaml

Do not force non-secret lifecycle/business configuration into .env.

This separation makes later production hardening easier.


3. DEVELOPMENT AUTHENTICATION

For the current development stage, the system should support:

SERVER_SUPERUSER_ID
SERVER_SUPERUSER_PASSWORD

These may be loaded from .env.

Existing Gateway superuser configuration may remain separate.

Server authentication and Gateway authentication must not be accidentally conflated.

.env must be excluded from Git.


4. BOOT CONFIGURATION

The boot configuration defines the starting scope of the system.

Minimum fields should include:

- lifecycle_stage
- global_asset_classes
- implemented_asset_classes
- current_focus
- simulation_focus

Initial required values:

lifecycle_stage:
PRE_ALPHA

implemented_asset_classes:
- EQUITIES
- OPTIONS_ON_EQUITIES

The phrase OPTIONS_ON_EQUITIES should be used rather than generic OPTIONS because future versions may support options on other underlyings.

Possible future asset classes may include, for example:
- fixed income
- commodities
- futures
- currencies / FX
- crypto assets
- options on futures
- options on indices
- other derivatives

The initial system should not imply that all possible asset classes are already implemented.


5. GLOBAL ASSET CLASS LIST

The Metadata Engine maintains a global list of asset classes known to the architecture.

This global list may be broader than what is currently implemented.

Separate the concepts:

KNOWN / GLOBAL ASSET CLASSES
versus
CURRENTLY IMPLEMENTED ASSET CLASSES

This distinction is important.

Example:

Global list:
- EQUITIES
- OPTIONS_ON_EQUITIES
- FIXED_INCOME
- FUTURES
- COMMODITIES
- FX
- CRYPTO
- OPTIONS_ON_FUTURES
- OPTIONS_ON_INDICES

Currently implemented:
- EQUITIES
- OPTIONS_ON_EQUITIES

The exact initial global list may be small and expandable.


6. SIMULATION FOCUS

The initial simulation/testing focus should explicitly identify what is being simulated.

Current initial focus:
OPTION PRICES for OPTIONS_ON_EQUITIES

The system may require underlying equity/reference data to support those simulations.

Suggested boot field:

simulation_focus:
- OPTIONS_ON_EQUITIES_PRICING

or equivalent structured representation.

Avoid a vague string if the codebase already has typed configuration structures.


7. METADATA ENGINE RESPONSIBILITY

The Metadata Engine is a startup initializer and verifier of global metadata.

At startup, the COO starts the Metadata Engine before the Reference Data Engine.

The Metadata Engine is responsible for ensuring that four global metadata datasets/tables exist and are populated sufficiently for the current boot configuration.

The four required metadata datasets are:

1. Agent Names
2. Global Asset Classes
3. Implemented List
4. Focus List


8. TABLE / DATASET 1 — AGENT NAMES

Purpose:
Provide unique human-style names for newly created persistent agents.

Initial requirements:

- maintain a pool of available names
- one name per agent is sufficient
- names must be unique among persistent agents
- assignment must be atomic
- assigned names must be removed from or marked unavailable in the available pool
- agent name must be persisted as part of agent identity
- restart must not reallocate a different name

Possible fields:

name_id
name
status = AVAILABLE | ASSIGNED
assigned_agent_id
assigned_at

When agent creation occurs:

1. reserve available name
2. create stable agent identity
3. bind name to agent
4. persist agent
5. mark name ASSIGNED

Do not allocate the same name twice.


9. TABLE / DATASET 2 — GLOBAL ASSET CLASSES

Purpose:
Represent asset classes recognized by the overall architecture.

This is not the same as current implementation.

Possible fields:

asset_class_id
code
display_name
description
enabled_for_architecture
created_at

Initial entries should include at minimum:

EQUITIES
OPTIONS_ON_EQUITIES

Additional future classes may be pre-seeded or added later.


10. TABLE / DATASET 3 — IMPLEMENTED LIST

Purpose:
Represent what the system can actually execute today.

At the start of this milestone:

- EQUITIES
- OPTIONS_ON_EQUITIES

Nothing else should be falsely marked implemented.

Possible fields:

capability_id
capability_type
code
status
version
implemented_at
notes

The design should allow more than asset classes later if "implemented list" becomes a broader capability registry.


11. TABLE / DATASET 4 — FOCUS LIST

Purpose:
Represent what the development/training/simulation system is focused on right now.

Initial focus should include:

- EQUITIES as supporting underlying/reference domain
- OPTIONS_ON_EQUITIES
- option-price simulation
- pre-alpha startup/observability
- initial agent-training pipeline

Possible fields:

focus_id
focus_type
code
priority
active
description
start_time
end_time

This list can change without redefining the entire architecture.


12. METADATA ENGINE STARTUP ALGORITHM

On COO startup:

1. Publish:
   METADATA_ENGINE_STARTING

2. Load boot configuration.

3. Verify Agent Names dataset exists.
   If missing:
   - create
   - seed with configured initial names

4. Verify Global Asset Classes dataset exists.
   If missing:
   - create
   - seed at least EQUITIES and OPTIONS_ON_EQUITIES

5. Verify Implemented List exists.
   If missing:
   - create
   - seed EQUITIES and OPTIONS_ON_EQUITIES

6. Verify Focus List exists.
   If missing:
   - create
   - seed current pre-alpha focus

7. If structures exist:
   - do not blindly recreate
   - validate them
   - apply idempotent missing seed data where appropriate

8. Publish summary:
   names_available = N
   global_asset_classes = N
   implemented_items = N
   active_focus_items = N

9. Publish:
   METADATA_READY

10. Enter IDLE state.

The Metadata Engine has no need to continuously consume resources once its startup work is complete unless later asked to perform a metadata operation.


13. IDEMPOTENCY

Metadata initialization must be idempotent.

Running startup multiple times must NOT:
- duplicate asset classes
- duplicate names
- overwrite existing name assignments
- reset agent identity
- duplicate focus rows unnecessarily
- destroy operator changes without explicit instruction

Startup should be safe after:
- normal shutdown
- crash
- restart
- repeated developer runs


14. STARTUP DEPENDENCY

The required startup dependency is:

LOGIN
-> COO
-> LOAD STAGE / BOOT CONFIG
-> METADATA ENGINE
-> METADATA_READY
-> REFERENCE DATA ENGINE
-> SIMULATION / EDUCATION / TRAINING PIPELINE AS INPUTS BECOME AVAILABLE

Reference Data Engine must not begin normal work before metadata readiness has been established.

This does not mean every later engine must wait for every earlier engine to completely finish its universe.

Only the Metadata Engine has a hard startup gate here.

After that, downstream components should use readiness thresholds and parallelism.


15. REFERENCE DATA ENGINE RELATIONSHIP

Once Metadata Engine reports ready:

Reference Data Engine starts.

For pre-alpha:
- it does not need the complete universe of securities
- an approximate/small useful universe is acceptable
- the goal is to provide enough valid reference data for simulation and training flow to begin

If usable reference data already exists:
- verify it
- report readiness
- avoid rebuilding unnecessarily

If more data is needed:
- begin generation/population
- publish progress

As soon as a usable minimum exists:
- publish REFERENCE_DATA_MINIMUM_READY

That event may allow Simulation Engine to begin.


16. SIMULATION AND EDUCATION RELATIONSHIP

Simulation should begin once enough reference data exists.

Education Department should begin curriculum work as soon as there is some usable:
- reference data
- simulation data

It must not wait for complete datasets.

As soon as a curriculum item is ready:
- publish CURRICULUM_ITEM_READY
- make it available to the training subsystem

This creates a streaming/parallel startup pipeline rather than a giant sequential batch.

18. STATUS MESSAGES REQUIRED

At minimum, the COO should be able to display messages similar to:

Metadata Engine starting
Boot configuration loaded
Lifecycle stage: PRE_ALPHA
Agent Names metadata verified
Global Asset Classes metadata verified
Implemented List verified
Focus List verified
Metadata ready
Metadata Engine idle
Reference Data Engine starting

The exact wording is not important.

The visibility and correctness of state transitions are important.


19. DEFINITION OF DONE

This specification is complete when:

1. Server Superuser development credentials are supported.
2. Boot config exists outside secret configuration.
3. PRE_ALPHA lifecycle stage is loaded.
4. EQUITIES and OPTIONS_ON_EQUITIES are identified as implemented.
5. Option-price simulation focus is represented.
6. Metadata Engine starts automatically under COO startup.
7. Four metadata datasets exist:
   - Agent Names
   - Global Asset Classes
   - Implemented List
   - Focus List
8. Metadata initialization is idempotent.
9. Metadata readiness is observable in the COO feed.
10. Reference Data Engine starts only after METADATA_READY.
11. Agent name reservation is unique and persistent.
12. The Metadata Engine enters idle state after completing startup work.
