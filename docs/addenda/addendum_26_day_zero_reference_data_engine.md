Project Jarvis Specification

Day Zero Reference Data Engine

Status: Design Specification Priority: Highest Day Zero Dependency
Purpose: Establish the canonical reference-data foundation required
before operational agents begin work.

1. Architectural Role

The Reference Data Engine is the first shared domain engine initialized
during Day Zero.

It owns the creation, validation, maintenance, and serving of canonical
reference metadata used by the rest of the organization.

The Reference Data Engine is an engine, not an autonomous organizational
authority. It performs a defined infrastructure function under
orchestration.

2. Ownership and Startup Authority

The COO is responsible for instantiating and running the Reference Data
Engine during the Day Zero startup sequence.

The CEO remains strategic and constitutional rather than directly
operating infrastructure engines.

The startup relationship is:

Bootstrap → Controller → COO orchestration → Reference Data Engine →
readiness certification → downstream initialization.

The Controller retains system-level orchestration authority and
lifecycle knowledge. The COO coordinates operational readiness and
dependencies.

3. Day Zero Rule

No operational Explorer, Speculator, Analyst, or other data-dependent
agent should begin normal work until the minimum required reference-data
foundation has been created and certified ready.

Reference data therefore precedes market-data exploration and simulated
organizational activity.

4. Core Responsibilities

The Reference Data Engine shall build and maintain:

-   Asset Universe
-   Capability Set
-   Current Focus
-   Asset Class registry
-   Security / Instrument Master
-   Asset identifiers and identifier mappings
-   Issuer Master
-   Exchange and venue metadata
-   Currency metadata
-   Trading-calendar metadata
-   Symbol mappings
-   Instrument relationships
-   Corporate-action reference metadata where available
-   Provenance, validation, and version history

5. Asset Universe Model

Three concepts must remain distinct.

5.1 Asset Universe

The long-term universe of asset classes and instrument types that the
organization is interested in understanding or eventually supporting.

5.2 Capability Set

The subset of the Asset Universe that the system can currently process
correctly.

5.3 Current Focus

The subset currently selected for active research, simulation, training,
or operation.

These are living registries. They can expand or contract as the
organization learns and its capabilities change.

6. Asset-Class Granularity

Asset classes should be defined at the level at which system capability
materially differs.

For example, the system must not hide an inability to process options
merely by saying it supports “equities.”

Possible distinct classes include:

-   stocks
-   stock options
-   futures
-   futures options
-   commodities
-   commodity options
-   currencies / FX
-   fixed-income instruments
-   ETFs and other fund instruments
-   digital assets

The catalog must be extensible. Missing asset classes can be added
without redesigning downstream systems.

7. Identifier Architecture

The system must not assume that every instrument has a CUSIP or any
other universal identifier.

Identifier requirements are metadata-driven.

For every asset class, the engine must be able to define:

-   applicable identifier types
-   required identifiers
-   optional identifiers
-   uniqueness constraints
-   multiple identifiers per instrument
-   mappings among external identifiers
-   canonical internal asset ID

The canonical internal asset ID is the stable key used by Jarvis
internally.

External identifiers are attributes and mappings around that canonical
identity.

8. Security / Instrument Master

The Security Master is the canonical catalog of tradable instruments
known to the system.

Its long-term purpose is broad coverage of tradable assets.

Day Zero does not require complete global coverage. It requires a valid
architecture and sufficient populated assets for the Current Focus.

At minimum, each instrument should be resolvable to:

-   canonical asset ID
-   asset class
-   primary symbol where applicable
-   exchange or venue where applicable
-   applicable external identifiers
-   issuer or underlying relationship where applicable
-   active/inactive status
-   source provenance
-   validation status

9. Assets Table

The Assets table is the primary work-discovery seed for downstream
agents.

Its initial purpose can remain deliberately simple: provide the
canonical list of assets/identifiers that Explorers can iterate over.

Once Assets is populated and certified, Explorers no longer need to
invent, guess, or independently discover the system’s canonical
instrument identity.

10. Free Reference-Data Sources

Day Zero should preferentially bootstrap from legally usable free/public
sources where practical.

Candidate source categories include:

-   SEC EDGAR and other regulator/public filings
-   exchange and venue symbol directories
-   OpenFIGI where its terms and API limits permit
-   issuer disclosures
-   public trading calendars
-   public classification/reference datasets
-   other validated free sources added through adapters

Source-specific logic must be isolated behind adapters so sources can be
added, removed, replaced, or upgraded without changing the canonical
data model.

Licensing, attribution, redistribution rights, rate limits, and source
terms must be respected.

11. Ingestion Architecture

Each source adapter should follow a common pipeline:

Acquire → Parse → Normalize → Validate → Resolve Identity → Merge →
Record Provenance → Publish.

Raw source values should not silently overwrite canonical values.

Conflicts must be resolved using explicit source-priority and confidence
rules.

12. Provenance and Auditability

Every material canonical value should be traceable, where practical, to:

-   source
-   retrieval time
-   source identifier
-   transformation/version
-   validation result
-   confidence or authority ranking where relevant

Corrections should be auditable.

The system should favor versioned correction over invisible mutation.

13. Idempotency

The Reference Data Engine must be safe to run repeatedly.

Running the same ingestion process twice against unchanged inputs must
not create duplicate assets or corrupt mappings.

Startup should therefore be deterministic and idempotent.

14. Data Quality and Certification

Before signaling readiness, the engine must perform automated checks
including:

-   schema validity
-   required-field completeness
-   duplicate detection
-   identifier uniqueness
-   identifier collision detection
-   broken relationships
-   unsupported asset classes
-   stale/inactive instruments where detectable
-   source conflicts
-   minimum Current Focus coverage

Readiness is not equivalent to perfection.

It means the reference dataset satisfies the explicit requirements of
the current operational phase and Current Focus.

15. Lifecycle Separation

The Reference Data Engine should not need to reason about Pre-Alpha,
Alpha, Beta, or Live as organizational concepts unless explicitly
required for its own data behavior.

Lifecycle knowledge remains at the orchestration layer.

Downstream agents should ask for assets/reference data through stable
interfaces rather than infer lifecycle state.

16. Interface Contract

The engine should expose stable programmatic interfaces for operations
such as:

-   get asset by canonical ID
-   resolve external identifier
-   resolve symbol + venue
-   list assets by asset class
-   list Current Focus assets
-   retrieve identifier mappings
-   retrieve issuer information
-   retrieve exchange/venue information
-   retrieve trading-calendar information
-   query provenance
-   query validation state

The implementation may use database access, services, APIs,
repositories, or combinations thereof, but consumers should depend on
contracts rather than storage internals.

17. Failure Behavior

If the Reference Data Engine cannot establish minimum required reference
data:

1.  It must not falsely signal readiness.
2.  It must report the failed prerequisite.
3.  The COO must keep dependent operational agents blocked.
4.  Diagnostics must identify the failed source, validation, mapping, or
    coverage requirement.
5.  Recovery/retry should be possible without rebuilding the entire
    system unnecessarily.

18. Readiness Signal

When minimum reference-data requirements have been satisfied, the
Reference Data Engine issues a readiness/certification result to the
COO.

The COO can then proceed to the next Day Zero/Day One dependency.

19. Initial Downstream Dependency

Once the Security Master and Assets table are ready, the Explorer can
begin consuming the canonical asset list.

The initial Explorer research focus discussed is volatility surfaces.

The Explorer should not maintain a competing security master.

20. Testing Requirements

The implementation should include automated:

-   unit tests
-   source-adapter tests
-   normalization tests
-   identifier-resolution tests
-   duplicate/collision tests
-   database constraint tests
-   integration tests
-   restart/idempotency tests
-   failure/recovery tests
-   readiness-gate tests

User Acceptance Testing follows implementation and integration testing.

21. Acceptance Criteria

The first version is acceptable when it can:

1.  Start against an empty supported database.
2.  Create or use the required reference-data schema.
3.  Ingest configured free/public sources.
4.  Normalize records into the canonical model.
5.  Generate stable internal asset IDs.
6.  Populate the initial Asset Universe, Capability Set, and Current
    Focus.
7.  Populate the Security Master and Assets table for the initial focus
    universe.
8.  Resolve supported external identifiers consistently.
9.  prevent duplicate canonical instruments under repeated ingestion.
10. record provenance for canonical records.
11. detect and report material source conflicts.
12. survive restart and rerun safely.
13. fail closed when minimum reference-data requirements are not met.
14. certify readiness to the COO when requirements are met.
15. provide stable interfaces to downstream engines and agents.

22. Day Zero Position

The Reference Data Engine is the first major data foundation.

The intended dependency chain is:

Empty System → Bootstrap → Controller → Schema Initialization → COO
Operational Orchestration → Reference Data Engine → Asset Universe /
Capability / Focus → Identifier Architecture → Security Master / Assets
→ Reference Data Certification → Next required data-world initialization
→ Operational agents.

This specification should remain focused on reference/master data.
Market-data generation, simulation-world construction,
volatility-surface generation, speculation, analysis, and evaluation
belong in their respective engine/agent specifications.
