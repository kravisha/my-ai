My AI
Desktop Runtime & Living Workspace Specification
Persistent COO • Native Desktop • Animated Executive Presenter • Role-Based Gateway
Draft v1.0  |  25 August 2026
1. Purpose
This specification defines the next evolution of My AI from a browser-hosted application into a persistent native desktop runtime whose primary visible identity is the COO. The system must feel less like software that is launched and more like a coherent intelligence that sleeps, wakes, remembers, resumes, presents, listens, and acts.
Core idea: The user does not “open an app.” The user wakes the same persistent COO and reconnects to the same living organization.
2. Product Vision
Move the current web interface into a proper desktop application without breaking the underlying service architecture.
Make the COO the persistent root object and executive runtime of the local organization.
Restore the complete workspace on startup, including unfinished user input, active conversations, selected tabs, layouts, dashboards, and work in progress.
Make voice the primary interaction channel, while keyboard, mouse, touch, and direct visual controls remain optional.
Present operations as a live, animated executive briefing rather than a static terminal or dense dashboard.
Retain a browser-accessible Gateway as a secure, role-scoped window into the same running organization.
Architect every choice so this desktop runtime can evolve toward an AI-first operating environment in which the COO becomes the user-facing system itself.
3. Non-Negotiable Design Principles
Persistent identity: The COO is not recreated conceptually on every launch. Its identity, state, history, role, configuration, workspace, and relationships persist across restarts.
Bootstrap, do not “run”: The entrypoint exists only to restore or create the COO root object and hand control to it.
Everything resumes: If state can reasonably be preserved, it must be preserved. The system should assume state matters unless explicitly marked disposable.
One organization, many windows: Desktop, browser Gateway, future mobile surfaces, and other interfaces are views into one organization, not separate brains.
Intent over applications: The user asks for outcomes. The COO chooses tools, services, APIs, files, or agents needed to produce the result.
Voice first, not voice only: The ideal path requires no keyboard or mouse, but conventional input remains available whenever useful.
Presentation follows reality: Animations, highlights, speech, gestures, and dashboards must represent real system state. Motion is informative, not decorative noise.
Interruption is first-class: The user can interrupt the COO at any moment. The COO immediately yields, answers, changes the visual focus, and can later resume the briefing.
4. System Lifecycle
4.1 Minimal Bootstrap
The startup entrypoint should remain intentionally small. A representative conceptual flow is:
Initialize minimum platform services.
Locate the persisted COO identity and latest valid state checkpoint.
Restore the COO root object, or create it only on first installation.
Reconnect the COO to managers and services required by the current machine.
Rehydrate the workspace and presentation state.
Resume recoverable work.
Hand all ongoing control to the COO runtime.
Hard invariant: main.py (or equivalent launcher) must not become the business application. It is a bootstrapper only.
4.2 Shutdown, Sleep, Crash, and Restart
Normal shutdown should behave like putting the organization to sleep. Abnormal termination should still recover from the latest durable checkpoint. A restart should feel like waking the same entity, not starting a new session.
5. Persistence Specification
5.1 Persistence Philosophy
Persistence is a foundational behavior, not a feature added later. The system should continuously checkpoint meaningful state. The user should not need to press Save to preserve the living workspace.
5.2 State That Must Persist
COO identity, configuration, name, role, personality configuration, operational state, and long-term references.
Organization and agent registry, including active, paused, waiting, and recoverable agents.
Task state, queues, assignments, dependencies, progress, retries, blockers, and completion history.
Inter-agent collaboration threads and personal inbox-style communications.
Open conversations, conversation positions, filters, selected agents, and contextual views.
All open tabs, panels, windows, docking state, sizes, positions, selected items, scroll position, zoom level, and display mode.
User drafts, including text typed into an input field even if Enter or Send has never been pressed.
Voice interaction state that is meaningful to resume, such as interrupted question context or pending confirmation.
Dashboard configuration, live briefing position, presenter topic, current visual focus, and highlighted data.
Files currently being worked on, references to source materials, output locations, and unsaved application-level edits managed by My AI.
Pending notifications, acknowledgements, escalation state, and decisions awaiting the user.
Permissions, authenticated role context, gateway session metadata where policy permits, and audit references.
User preferences for layout, presentation density, briefing style, speech, accessibility, and input mode.
5.3 Draft Text Requirement
Any partially typed text is considered user intent and must be checkpointed incrementally. If the user types half a sentence and the machine crashes before Send, the same text must be present in the same field after recovery. This requirement applies to command boxes, chat input, notes, search fields that represent ongoing work, and other editable workspace surfaces.
5.4 Durable State vs. Reconstructed State
The system may reconstruct resources that are inherently transient, such as process handles, network sockets, GPU contexts, or renderer instances. However, it must persist enough declarative state to reconstruct them so the user-visible result resumes coherently.
6. COO as the Root Object
6.1 Responsibility
The COO is the long-lived executive root of the runtime. It owns the organization conceptually, but should not contain every implementation detail directly. It coordinates specialized managers and services so that the COO remains stable while components evolve.

7. Desktop Application Architecture
7.1 Native Shell
The next implementation should use a native desktop shell rather than making the browser the primary host. The browser Gateway remains supported, but the desktop command center should behave as a resident workspace with native startup, persistence, audio, display, and device integration.
The UI layer must remain separable from COO logic. The backend should not care whether the current window is native desktop, browser Gateway, future mobile, or another surface.
7.2 Recommended Implementation Shape
Desktop shell: native windowing and lifecycle host.
Local COO runtime: long-lived process or service responsible for restoring the COO root.
Local database: durable source of operational state and communication; database-first messaging remains acceptable.
Renderer/presenter layer: real-time visual composition and animation.
Voice services: microphone capture, speech recognition, turn detection, TTS, interruption handling.
Service adapters: file system, email, spreadsheets, browsers, APIs, external tools, and future hardware interfaces.
Gateway endpoint: authenticated, role-aware remote window into the runtime.
8. Look and Feel: “Live Executive Broadcast”
8.1 Visual Direction
The current Bloomberg-terminal feeling should evolve toward a modern CNBC/CNN-style live command center: visual, approachable, narrative, dynamic, and easy to understand at a glance. It should still be information-rich, but not visually punishing.
Use strong visual hierarchy instead of dense walls of text.
Use large, readable status modules, charts, agent activity cards, and concise live tickers when useful.
Animate state changes smoothly so the user can see work moving through the organization.
Keep important exceptions prominent and routine success quiet.
Avoid decorative animation that does not communicate system state.
8.2 The Animated Executive Presenter
The central presentation metaphor is a live executive presenter in an operations studio. The presenter is the visible embodiment of the COO for the primary operator experience.
The presenter appears as a believable animated person, not a pulsing dot or static portrait.
The presenter can sit at a desk, stand, turn toward displays, maintain eye contact, and react naturally while listening.
Facial expression, gaze, posture, lip movement, and gesture should support the spoken interaction.
The presenter behaves like a television anchor, weather presenter, and operating executive combined: narrating the live organization while manipulating supporting displays.
The presenter must remain subordinate to the actual intelligence. The avatar is a presentation layer, not the brain.
8.3 Studio Environment
Behind or beside the presenter is a virtual operations display containing the actual tabs, dashboards, agent conversations, tasks, market information, system health, and other relevant views. The system can bring a panel forward, enlarge it, split the screen, zoom into a detail, or return to a broader studio view as the conversation demands.
8.4 Pointer and Annotation Behavior
The presenter should have a virtual pointer, analogous to a laser pointer or broadcast touchscreen tool.
Point to a tab, card, chart, line, agent, task, or event being discussed.
Bring a referenced tab or panel to the foreground.
Trace along a line or timeline while explaining it.
Circle, underline, bracket, or temporarily annotate relevant regions.
Zoom or spotlight a detail and then restore the broader view.
Synchronize pointer motion and annotation with the spoken explanation.
Clear temporary annotations automatically when the discussion moves on, unless the user asks to keep them.
8.5 Live Narration
The COO can proactively run a briefing when useful: what completed, what is underway, what is blocked, what changed, what requires attention, and what the organization recommends next. The visual display must track the narration in real time.
8.6 Interruption Model
The user can interrupt naturally at any point by voice or other input. On interruption the presenter should stop promptly, listen, visually acknowledge the user, answer the question, change the display focus if needed, and then either resume the previous briefing or abandon it based on the conversation.
Behavioral goal: The interaction should feel like interrupting a capable human executive who has full command of the room, not like stopping a prerecorded presentation.
9. Core Operational Views
9.1 Agent Conversations
Provide an adjustable “Agent Conversations” view showing live collaboration across the organization. It is a map of collaboration, not merely a raw log.
Thread conversations by task, topic, participants, team, or time.
Filter to one agent, one team, cross-team traffic, or organization-wide activity.
Allow the user to expand from summary into full context.
Show conversation state clearly: Active, Waiting, Completed.
Allow the COO presenter to jump directly into a conversation and explain what is happening.
9.2 Other First-Class Views
Organization overview and agent status.
Task queues, dependencies, blockers, and completion flow.
Alerts and exceptions requiring operator attention.
Training, evaluation, and evolution activity.
System and machine health.
Market/simulation/analytics views where relevant.
Personal inboxes and collaboration requests.
Audit/reason history where the operator is authorized to inspect it.
10. Natural-Language Interface
Every major visual view must also be queryable in natural language. The user should be able to ask questions such as “What is everyone working on?”, “Why is this task delayed?”, “Show me the conversation between Explorer and Analyst”, or “What changed while I was away?” The COO interprets the request, queries the same underlying organizational data, changes the visual focus, and answers conversationally.
Natural language is not a separate reporting system. It is another control surface over the same source of truth.
11. Voice-First Human Interface
The default user experience should work without a keyboard or mouse. A microphone, speaker, and visual display are sufficient for normal operation. Conventional input devices remain optional and can be used at any time.
Wake or address the COO by name.
Ask for information conversationally.
Issue tasks in outcome language rather than application language.
Request visual changes: “show that tab,” “zoom in,” “compare these,” “go back,” “open the agent conversation.”
Interrupt speech naturally.
Confirm consequential actions when policy requires confirmation.
12. Intent-Based Work Model
The system should progressively hide application mechanics. For example, the user should be able to say: “Take last year’s rental accounting file, update it for this year using the information I give you, show me the result, and send it to my accountant.” The COO determines whether that requires a spreadsheet engine, file operations, calculations, email, or specialist agents. The user thinks in goals, not apps.
Future OS direction: Applications become implementation tools behind the COO. The user interacts primarily with intent and results.
13. Gateway Architecture
13.1 Gateway Principle
The Gateway is a secure browser-accessible window into the same running organization. It must never create a duplicate COO, duplicate organization, or independent source of truth unless explicitly running a separate tenant.
13.2 Role-Based Experience
13.3 Personal Agent Experience
For most non-COO users, the Gateway should feel less like a dashboard and more like approaching a trusted representative. The user can talk to a named, animated agent that knows the permitted context, answers questions, performs allowed tasks, and reaches deeper organizational capabilities on the user’s behalf.
14. Security and Isolation Requirements
All Gateway access must be authenticated and role-scoped.
The presentation layer must never bypass backend authorization just because information exists on the server.
Sensitive operational views must be withheld from roles that do not require them.
External agents must expose only approved capabilities and data.
State persistence must encrypt secrets and sensitive credentials according to the broader system security architecture.
The desktop presenter must not accidentally surface restricted data during a shared-screen or demo mode.
15. Failure Handling and Recovery
Persist state incrementally rather than only on exit.
Use atomic checkpoints or transactional state writes so a partial save cannot corrupt the last known good state.
Maintain schema/version metadata for forward migrations.
On recovery, clearly distinguish successfully resumed work from work that must be retried or revalidated.
Do not silently repeat consequential external actions after a crash. Use idempotency keys, completion markers, or explicit reconciliation.
If a renderer or avatar subsystem fails, the COO must remain usable through fallback text/voice interfaces.
If voice fails, keyboard/mouse/touch must remain available.
16. Performance and Experience Targets
17. Scalability and Distribution
The current implementation may run on one computer, but the architecture must assume eventual distribution. The database may run on its own server; simulation, market data, agent groups, and other services may run on separate machines. The COO desktop remains the operator’s coherent window into the organization regardless of where the work executes.
A database-first communication architecture remains valid. Agents may receive work and collaboration messages through well-defined database tables or an abstraction over them. A message broker is not required by this specification.

PASS when: The user can operate core functions by voice without requiring keyboard or mouse.
PASS when: The user can interrupt the COO while it is speaking and receive an immediate context-aware response.

PASS when: The COO can answer natural-language questions by querying the same underlying operational data shown in the UI.
PASS when: The animated presenter can direct attention to a real UI element using synchronized pointing/highlighting.
PASS when: The presenter can bring a relevant panel forward during explanation and return to the previous layout.
PASS when: A renderer/avatar failure does not terminate the COO runtime.
PASS when: The Gateway presents different information and controls based on authenticated role.
PASS when: An external client can interact with a named personal agent without receiving unauthorized internal views.

20. Reference User Experience
The operator starts the computer and opens My AI. The same COO appears in the same studio and the same workspace returns. A partially typed question from before shutdown is still present. The COO greets the operator and begins a concise live briefing: what completed, what is active, and what needs attention. As the COO speaks, the relevant panels move forward and the presenter points to the corresponding information.
The operator interrupts: “Wait. What is happening between Explorer and Analyst?” The COO stops, turns attention to the operator, opens Agent Conversations, highlights the active thread, and explains it. The operator asks a follow-up. The COO answers, optionally assigns work, and then asks whether to resume the earlier briefing. No menus were required. No application workflow had to be remembered. The user interacted with one coherent organization.
21. Architectural North Star
This desktop migration is not merely a change from browser to native UI. It is the first deliberate step toward an AI-first computing model. Today, the COO runs on top of a conventional operating system. Over time, conventional applications become increasingly invisible tools behind the COO. Eventually, the system can evolve toward a minimal host in which the COO is the primary intelligence the user encounters from boot onward.
North-star sentence: Do not design a better collection of applications. Design one persistent intelligence that can use everything else.
