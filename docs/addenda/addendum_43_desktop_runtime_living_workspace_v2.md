MY AI — DESKTOP RUNTIME & LIVING WORKSPACE SPECIFICATION

1. PURPOSE

Define the desktop form of My AI as a persistent, native, living workspace rather than a conventional web application.

The system must feel as though the user is waking an already-existing intelligence and organization, not launching a disposable program.

The desktop application is the primary operator interface for the COO and the wider agent organization. It must preserve continuity, state, identity, work context, and active interaction across shutdowns and restarts.

2. CORE DESIGN PRINCIPLE

The user does not "start an app."

The user wakes a persistent COO and reconnects to an ongoing organization.

The visible interface is only a presentation layer over the living system.

3. BOOTSTRAP MODEL

The main bootstrap program must remain extremely small.

Conceptual responsibility of main.py:

1. Start runtime prerequisites.
2. Locate the latest compatible COO implementation.
3. Load persisted COO state.
4. Apply state migrations if required.
5. Instantiate the current COO.
6. Inject restored state into the COO.
7. Restore the user workspace.
8. Hand over control completely to the COO.

main.py must not contain business behavior.

main.py must not own dashboards, agents, task logic, conversations, or presentation behavior.

The COO is the long-lived root object of the organization.

4. NATIVE DESKTOP FIRST

The primary operator experience should migrate away from being browser-dependent.

The desktop application should use a native desktop shell.

The backend and COO runtime must remain independent of the desktop shell so that additional interfaces can later be added.

The front end may be replaced without rewriting the COO.

5. PERSISTENT LIVING WORKSPACE

The application must preserve the user's working environment continuously.

Persistence should include, where applicable:

- Open tabs
- Active panels
- Window layout
- Current selected agent
- Current selected task
- Open conversations
- Scroll positions
- Filters
- Search state
- Expanded or collapsed panels
- Draft text
- Half-typed messages
- Unsubmitted natural-language queries
- Current briefing position
- User preferences
- Active alerts
- Agent status
- Task status
- Conversation status
- Current studio state
- Presenter state
- Relevant temporary workspace state

The design philosophy is:

THE USER DOES NOT SAVE. THE SYSTEM REMEMBERS.

6. CRASH RECOVERY

The application must recover from abnormal termination with minimal perceptible state loss.

The system should checkpoint important UI and interaction state incrementally.

A crash should not destroy a half-typed message.

A restart should feel like waking the same system.

7. SEPARATION OF INTERFACE AND CONTENT

The interface may evolve substantially while persisted content remains stable.

Persisted state must therefore be separated from UI implementation details wherever practical.

The UI should reconstruct itself from persisted semantic state.

A new UI version must be able to load old state through migration logic or safe defaults.

8. COO AS ROOT OBJECT

The COO should be treated as the organizational root object.

The COO owns orchestration conceptually, but should not contain every implementation detail directly.

The COO may coordinate or hold references to components such as:

- Agent registry
- Task system
- Collaboration system
- Display manager
- Presenter controller
- Voice interface
- Persistence manager
- Gateway manager
- Security layer
- Event/history layer
- Natural-language query interface

The COO is the conductor, not the entire orchestra.

9. VOICE-FIRST INTERACTION

Voice is the primary interaction model.

Mouse and keyboard remain optional.

The user should be able to perform normal work through intent alone.

Examples:

"Show me what everyone is working on."

"Open the agent conversations."

"Why is this task delayed?"

"Show me my rental summary."

"Update last year's accounting spreadsheet with this year's numbers."

"Send it to my accountant."

The system determines which tools, applications, APIs, files, or services are required.

10. VISUALS WHEN USEFUL

Voice-first does not mean voice-only.

The system must present visual information when visual representation is more efficient.

Examples:

- Charts
- Tables
- Documents
- Images
- Task boards
- Timelines
- Agent conversations
- Alerts
- Comparisons
- Financial information

11. NATURAL-LANGUAGE COMMAND LAYER

The desktop must include a natural-language interface over the same data shown visually.

The user should be able to ask questions about the live organization without navigating manually.

The conversational interface and the dashboard must refer to the same underlying state.

12. AGENT CONVERSATIONS VIEW

A dedicated Agent Conversations view should show collaboration across the organization.

It should support:

- Live conversations
- Threaded conversations
- Filtering by agent
- Filtering by team
- Filtering by task
- Filtering by time
- Expand/collapse
- Search
- Relationship context
- Request-for-information threads
- Task-related discussions
- Cross-team communication

Conversation state should be visually distinguishable as:

- Active
- Waiting
- Completed

This view should feel like a living map of organizational collaboration, not a raw log.

13. REAL-TIME OPERATIONS VIEW

The desktop should provide at-a-glance visibility into:

- Running agents
- Current tasks
- Queued tasks
- Stalled tasks
- Failed tasks
- Active collaborations
- Resource use
- Important alerts
- System health
- Recent completions

14. GATEWAY PRINCIPLE

The Gateway is not a second brain.

The Gateway is a secure window into the same living organization.

The server remains authoritative.

The Gateway exposes only the view and capabilities permitted for the current user.

15. ROLE-BASED GATEWAY EXPERIENCE

Different users receive different views.

COO-level user:
- May receive the full command-center experience.

Internal staff or agents:
- Receive role-relevant views and capabilities.

Clients:
- Usually interact with a personal representative agent rather than seeing the entire organization.

16. PERSONAL CLIENT AGENT

A client may be assigned a persistent personal agent with:

- Name
- Face
- Voice
- Identity
- Scoped memory
- Authorized access
- Relationship continuity

The client should feel as though they are speaking with a familiar representative of the organization.

17. ONE ORGANIZATION, MANY WINDOWS

The desktop app, web gateway, client interface, and future device interfaces must all connect to the same organizational state.

There must not be duplicate independent COOs for presentation convenience unless explicitly architected.

18. STARTUP EXPERIENCE

Startup should be visually calm and immediate.

The system should avoid traditional "application startup" behavior when possible.

Desired experience:

1. Runtime begins.
2. Persistent COO is restored.
3. Workspace appears.
4. Current state is already visible.
5. Presenter resumes naturally.
6. User can immediately speak.

The feeling should be continuity, not initialization.

19. SHUTDOWN EXPERIENCE

Shutdown should behave like sleep.

Before termination:

- Persist critical state
- Checkpoint drafts
- Persist workspace state
- Persist task metadata
- Persist conversation positions
- Record last known system state

The system should avoid requiring users to manually save.

20. FAILURE ISOLATION

The presentation layer must not be able to kill the COO.

If the animated presenter crashes:

- COO remains alive
- Tasks remain alive
- State remains intact
- Presenter can restart independently

If the desktop shell crashes:

- Backend remains available
- State remains recoverable
- Gateway can remain functional

21. IMPLEMENTATION PHILOSOPHY

Build simple now while preserving the future architecture.

The system may initially run on Windows and conventional operating-system services.

The architecture should nevertheless move toward the long-term AI-first computing model.

22. LONG-TERM DIRECTION

The future computer may boot into a persistent AI executive environment where conventional OS behavior is invisible to the user.

The low-level operating system may still exist, but it becomes plumbing.

The AI becomes the primary user-facing system.

23. ACCEPTANCE CRITERIA

The desktop runtime is successful when:

- It opens as a native desktop application.
- The COO is restored rather than recreated from scratch without history.
- The last workspace is restored.
- Half-typed text survives restart.
- Active tabs and panels survive restart.
- Conversations can be resumed.
- The user can control the system through natural language.
- Voice can serve as the primary interaction method.
- The desktop can recover from crashes.
- UI components can evolve without destroying persisted content.
- Gateway users can see role-scoped views of the same organization.
- The experience feels like reconnecting with an ongoing intelligence.
