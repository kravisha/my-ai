CLIENT-OWNED HOLDINGS + SUPERUSER PORTFOLIO SPECIFICATION
Version: 1.0
Status: Implementation-ready draft
Primary use: Claude / coding agent implementation
Scope: Portfolio ownership, isolation, simulated client data, superuser portfolio, and future Charles Schwab API integration

============================================================
1. PURPOSE
============================================================

The system must support portfolio analysis for multiple external clients while also supporting a separate Superuser portfolio.

The central design requirement is strict ownership isolation:

- Every client must have their own portfolio and holdings.
- A client must never be able to read, infer, query, or receive another client’s holdings.
- The Superuser portfolio must be stored and handled separately from all client portfolios.
- The Superuser portfolio must never be exposed through normal client-facing Gateway paths.
- Simulated data may be used initially.
- The architecture must support replacing simulated data with live brokerage data later, beginning with Charles Schwab.
- Brokerage integration must initially be read-only and analysis-only.
- The design must remain broker-agnostic so additional broker APIs can be added later.

============================================================
2. DESIGN PRINCIPLES
============================================================

2.1 Ownership before capability

Authorization must answer two separate questions:

1. Is this role allowed to invoke this capability?
2. Whose data is this capability allowed to read?

Passing the first check must never imply passing the second.

Example:
A Portfolio Analyzer may have permission to analyze portfolios, but it may only analyze the portfolio explicitly owned by the requesting client unless operating under an authorized Superuser context.

2.2 No shared portfolio state

Do not maintain one global portfolio file that is reused for multiple users.

Every portfolio object must have an explicit owner identity.

2.3 Default deny

If ownership is missing, ambiguous, stale, inconsistent, or cannot be verified, deny access.

Never fall back to the Superuser portfolio.
Never fall back to the first available portfolio.
Never infer ownership from UI state alone.

2.4 Read-only brokerage integration first

The first brokerage integration is for:

- positions
- holdings
- balances where available
- account metadata required for analysis
- other read-only portfolio information

Do not implement live order submission as part of this specification.

2.5 Broker abstraction

Portfolio analysis logic must not depend directly on Schwab-specific schemas.

Schwab is a provider, not the portfolio model.

============================================================
4. SUPERUSER PORTFOLIO
============================================================

4.1 Separate ownership domain

The Superuser portfolio is not a client portfolio.

It must have:

owner_type = SUPERUSER

It must never be represented as a client row merely for convenience.

4.2 Separate storage path

The implementation may use the same database, but ownership must remain structurally explicit and query-isolated.

If separate logical repositories or tables materially improve safety, that is acceptable.

The important requirement is that no normal client query can resolve to the Superuser portfolio.

4.3 Dedicated UI tab

Create a dedicated UI tab:

Superuser Portfolio

Requirements:

- Visible only when the authenticated user is the Superuser.
- Hidden entirely from normal clients.
- Must not be discoverable through client navigation routes.
- Must not be addressable merely by guessing a portfolio ID.
- Backend authorization remains mandatory even if the UI hides the tab.

4.4 Superuser portfolio contents

The Superuser Portfolio tab should eventually show:

- account selector if multiple Superuser brokerage accounts exist
- holdings
- symbol
- quantity
- average cost
- latest market value
- unrealized gain/loss where supported
- portfolio total value
- cash/balance information where supported
- asset-class breakdown
- analysis results
- risk metrics
- concentration
- options exposure
- timestamps and source
- sync state
- data freshness

4.5 Superuser analysis

The Superuser must be able to request analysis on the Superuser portfolio without exposing that data to client-facing agents or Gateway sessions.

============================================================
5. CLIENT-OWNED HOLDINGS
============================================================

5.1 One client, one or more portfolios

Each client may own one or more portfolios.

Every client portfolio must be associated with exactly one client owner.

5.2 No cross-client visibility

The following must all be blocked:

- Client A requesting Client B portfolio by ID
- Client A using a stale URL created by Client B
- an internal agent accidentally retaining Client B portfolio context while serving Client A
- a Gateway request that supplies a mismatched client_id and portfolio_id
- analysis generated using holdings from more than one client unless an explicitly authorized internal aggregate workflow exists

5.3 Ownership check

All portfolio retrieval should effectively behave like:

requested_portfolio.owner_id == authenticated_client.client_id

For Superuser requests, a separate explicit authorization path must exist.

Do not implement:

if superuser:
    skip all ownership checks

Instead, use explicit Superuser authorization plus explicit requested ownership context.

============================================================
9. GATEWAY SECURITY
============================================================

9.1 Gateway must receive owner context

Every portfolio-related request through the Gateway must resolve an authenticated owner context before portfolio retrieval.

Required conceptual context:

request_user_id
request_role
request_client_id if applicable
requested_portfolio_id
session_id
authorization_context

9.2 Never trust caller-supplied ownership

A client_id received from the front end is not sufficient proof of ownership.

Resolve authenticated identity on the server and verify portfolio ownership there.

9.3 No portfolio leakage through errors

Errors must not reveal:

- another client exists
- another client owns a requested portfolio ID
- symbols held by another client
- Superuser holdings
- brokerage account metadata

Preferred response:

Not authorized or resource unavailable.

9.4 Agent context isolation

When an AI agent receives portfolio context, it must receive only the holdings required for the current authorized task.

Do not load every portfolio into one agent context.

When a request changes clients, discard the previous portfolio context.

15. TEST REQUIREMENTS
============================================================

15.1 Ownership isolation tests

Required:

- Client A can view Client A portfolio.
- Client A cannot view Client B portfolio.
- Client B cannot view Client A portfolio.
- Client cannot view Superuser portfolio.
- guessed portfolio IDs do not bypass authorization.
- URL reuse does not bypass authorization.
- stale session context does not leak prior client data.

15.2 Superuser tests

- Superuser Portfolio tab visible for Superuser.
- tab not visible for Client.
- backend still denies client direct requests to Superuser portfolio.
- Superuser analysis uses Superuser holdings only.

15.3 Simulation tests

- simulated portfolios are distinct.
- simulation banner appears.
- simulation provider returns canonical schema.
- switching provider does not change analyzer contract.

15.4 Provider contract tests

Create a shared conformance test suite for all PortfolioProvider implementations.

Both:

SimulatedPortfolioProvider
SchwabPortfolioProvider

must satisfy the same canonical provider contract.

15.5 Security regression test

Reproduce the earlier isolation concern:

A client-facing Gateway request must never be able to receive the operator/Superuser portfolio merely because that is the only portfolio currently stored.

This should become a permanent regression test.

============================================================
17. FAILURE BEHAVIOR
============================================================

If broker API is unavailable:

- retain last valid snapshot if policy allows
- mark it stale
- do not silently claim it is current
- keep client isolation intact
- allow analysis only if stale-data policy permits

If authorization is unclear:

deny access.

If provider returns malformed data:

reject or quarantine it and preserve the last valid snapshot.

If account mapping is ambiguous:

do not guess.

============================================================
18. FUTURE BROKER EXPANSION
============================================================

The architecture must support later providers without redesigning portfolio ownership.

Potential future providers may include other brokerages or manual imports.

Adding another provider should require:

- provider adapter
- provider-specific authentication
- normalization mapping
- provider contract tests

It should not require rewriting:

- client ownership
- Superuser separation
- Gateway authorization
- Portfolio Analyzer
- UI ownership model
