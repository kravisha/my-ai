MY AI — EXECUTIVE PRESENTER & LIVE STUDIO EXPERIENCE SPECIFICATION

1. PURPOSE

Define the visual, animated, conversational experience of the COO as a live executive presenter inside My AI.

This is not a traditional dashboard.

This is not a Bloomberg-style terminal.

This is a living executive broadcast studio.

2. NON-NEGOTIABLE VISUAL DIRECTION

The interface must feel closer to a modern CNBC/CNN-style live briefing environment than to a Bloomberg Terminal.

Avoid:

- Dense grids of tiny numbers
- Terminal-like walls of text
- Excessive table density
- Monospaced financial-terminal aesthetics
- Static dashboards
- Screens filled uniformly with equal-weight information
- Raw developer-console appearance

Prefer:

- Strong visual hierarchy
- Large information surfaces
- Broadcast-style composition
- Focused panels
- Guided attention
- Animated transitions
- Live status strips
- Large charts when relevant
- Clean typography
- Presenter-led navigation
- Calm but visibly alive motion

Every major screen should feel as though the user has walked into a live briefing.

3. THE COO AS PRESENTER

The COO is represented visually by an animated human-like executive presenter.

Default COO identity:

Kumbhakarnan

He should be presented as a dignified, original character inspired by traditional Kumbhakarna royal imagery.

He is not a static avatar.

He is a live host.

4. CHARACTER APPEARANCE

Visual direction:

- Strong physical presence
- Regal demeanor
- Calm facial expression
- Intelligent and observant
- Approachable rather than intimidating
- Traditional royal-inspired attire
- Distinctive crown
- Rich but not costume-like visual language
- Original design
- Executive authority
- Warm human presence

Avoid copying any specific existing film, television, comic, game, or commercial depiction.

5. LIVE STUDIO

The COO exists inside a virtual operations studio.

The studio may include:

- Main presentation wall
- Secondary displays
- Agent activity panels
- Task status panel
- Conversation panel
- Market/data panels where relevant
- Alerts strip
- Organization health display
- Current briefing display
- Context-sensitive presentation surfaces

6. PRESENTER MOVEMENT

The COO should be able to:

- Stand beside displays
- Turn toward displays
- Turn toward the user
- Walk or shift position when appropriate
- Gesture naturally
- Maintain eye contact
- Point to information
- Pause while listening
- React to interruptions
- Resume presentation

7. POINTER TOOL

The COO should have a presentation pointer, conceptually similar to a laser pointer or smart annotation wand.

The pointer can:

- Highlight a tab
- Select a panel
- Trace a line
- Point to a number
- Circle a problem
- Underline a trend
- Mark a region
- Draw temporary annotations
- Trigger zoom
- Bring a panel forward
- Change presentation focus

Pointer behavior must always correspond to real information.

No meaningless animation.

8. LIVE BRIEFING BEHAVIOR

The COO may continuously brief the user when appropriate.

Examples:

"Three tasks completed while you were away."

"The simulation team is waiting on market data."

"Two agents are collaborating on TQ-27."

"This item needs your approval."

As the COO speaks:

- Relevant panel comes into focus.
- Pointer highlights the subject.
- Supporting information appears.
- Nonessential information visually recedes.

9. INTERRUPTIBILITY

The user must be able to interrupt at any time.

Example:

COO:
"The simulation team has completed..."

User:
"Wait. What's happening with this agent?"

Expected behavior:

1. COO stops speaking immediately.
2. COO visually acknowledges the user.
3. COO shifts attention.
4. Relevant view opens.
5. COO points to the requested information.
6. COO answers naturally.
7. COO may ask whether to resume the prior briefing.

Interruption is a first-class interaction primitive.

10. NATURAL CONVERSATION

The presenter should behave like a normal conversational partner.

Required qualities:

- Responsive
- Non-scripted
- Context-aware
- Able to listen mid-briefing
- Able to answer follow-up questions
- Able to switch topics
- Able to return to a prior topic
- Able to remember what was being discussed

11. VOICE

Voice is the primary interaction mechanism.

Voice behavior should support:

- Natural pacing
- Interruptions
- Low latency
- Contextual tone
- Brief answers when appropriate
- Detailed explanation when requested

12. FACIAL EXPRESSION

Facial animation should communicate attention and understanding.

Examples:

- Listening
- Thinking
- Acknowledging
- Explaining
- Concern when a problem is material
- Satisfaction when a task completes
- Neutral calm during routine status

Avoid exaggerated cartoon behavior.

13. BODY LANGUAGE

Body language should reinforce meaning.

Examples:

- Turn toward the user when interrupted.
- Turn toward data when explaining.
- Use open-hand gestures for summaries.
- Point precisely when referencing a specific item.
- Pause movement while listening.

14. DASHBOARD BEHAVIOR

Dashboards are not static pages.

They are presentation surfaces controlled by context.

The system should be able to:

- Bring one panel forward.
- Dim irrelevant panels.
- Expand a chart.
- Collapse a completed item.
- Pan to a different information surface.
- Zoom into a conversation.
- Open a task timeline.
- Show agent relationships.
- Return to overview.

15. CAMERA-LIKE MOVEMENT

The interface may use restrained camera-like transitions.

Examples:

- Smooth pan
- Controlled zoom
- Focus shift
- Panel expansion
- Studio scene transition

Motion should guide attention.

Avoid visual noise.

16. BROADCAST RHYTHM

The experience should have the rhythm of a professional live broadcast.

Examples:

- Main story
- Supporting graphic
- Status strip
- Presenter explanation
- User interruption
- Drill-down
- Return to overview

17. AGENT CONVERSATIONS IN STUDIO

Agent Conversations should be treated as a major visual surface.

The COO can say:

"Let me show you what Explorer and Analyst are discussing."

Then:

- Conversation view opens.
- Active thread is highlighted.
- Relevant lines are emphasized.
- COO explains why the conversation matters.

18. CNBC, NOT BLOOMBERG

This requirement must be repeated throughout implementation review.

If an implementation looks like a Bloomberg Terminal, it has failed the visual requirement.

The target is:

LIVE EXECUTIVE BROADCAST STUDIO.

Not:

DATA TERMINAL.

19. VISUAL DENSITY

Information density should be adaptive.

Overview:
- Low to moderate density.

Drill-down:
- Higher density allowed.

The user should not be forced to scan everything at once.

20. STATUS VISUALIZATION

Use visual treatment to distinguish:

- Active
- Waiting
- Completed
- Blocked
- Failed
- Needs attention

The exact visual style may evolve.

21. PERSISTENT PRESENTER STATE

The presenter experience should resume where appropriate.

Potentially persist:

- Current studio
- Active panel
- Briefing position
- Current topic
- Pending interruption
- Recent question
- Presenter mode
- Display layout

The presenter may restart independently from COO state if rendering fails.

22. PRESENTER FAILURE ISOLATION

The animated presenter is a presentation layer.

It must never own critical business state.

If the avatar fails:

- COO remains alive.
- Tasks remain alive.
- Conversations remain alive.
- Gateway remains available.
- Presenter restarts.

23. ROLE-BASED PRESENTATION

COO / operator:
- Full studio.

Internal user:
- Scoped studio.

Client:
- Personal agent experience.

Clients do not need the entire executive command center.

24. PERSONAL CLIENT AGENT VISUALS

A client-facing personal agent may also have:

- Stable name
- Stable face
- Stable voice
- Relationship continuity

The presentation model may reuse the same rendering framework with role-specific design.

25. FUTURE DEMO MODE

The architecture should preserve the ability to run a browser-delivered demonstration.

The demo should be driven by the same server-side organization state.

The browser is a window.

It is not a second COO.

26. SALES DEMO NORTH STAR

A future demonstration might show:

1. User opens the system.
2. Kumbhakarnan appears in the studio.
3. He says what happened while the user was away.
4. Panels animate behind him.
5. He points to a completed item.
6. User interrupts.
7. He immediately pivots.
8. He opens the requested view.
9. He explains it.
10. He resumes or asks whether to continue.

The viewer should leave thinking:

"Why isn't every computer like this?"

27. ACCEPTANCE CRITERIA

The experience is successful when:

- The interface does not resemble a Bloomberg Terminal.
- It clearly resembles a modern live briefing environment.
- Kumbhakarnan appears as a live presenter.
- He can speak, listen, gesture, and point.
- Visuals track the topic of conversation.
- The user can interrupt naturally.
- The system changes focus in response to conversation.
- The presenter can explain live organizational state.
- Motion is purposeful.
- The studio remains readable.
- The presentation layer can fail without taking down the COO.
- A browser client can later receive a scoped version of the same living organization.
