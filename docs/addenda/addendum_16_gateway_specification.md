PROJECT JARVIS
AI COMMUNICATION GATEWAY SPECIFICATION
Version 1.0 Draft

1. PURPOSE

The AI Communication Gateway is the single external communication interface for Project Jarvis.

Its immediate purpose is to eliminate the manual relay currently required between the human user, the specification and analysis AI, and the implementation AI.

The fundamental objective is:

ONE-HOP DEVELOPMENT.

The user should be able to speak through a voice-first interface on a phone and perform the complete development collaboration workflow without manually copying text, taking screenshots, downloading documents, uploading documents, or moving information between AI systems.

The Gateway performs that coordination behind the scenes.

2. DEVELOPMENT PHILOSOPHY

Project Jarvis adopts specification-driven development.

The project is being designed and implemented concurrently. Specifications are not documentation written after implementation. They are living engineering artifacts that guide implementation.

The operating cycle is:

DISCUSS → SPECIFY → STORE IN GIT → IMPLEMENT → REPORT CONCERNS → REVIEW → UPDATE SPEC → CONTINUE

The specification leads the code.

When implementation reveals a problem, limitation, ambiguity, or better architectural approach, that information flows back into the specification process.

3. GIT AS THE DURABLE SOURCE OF TRUTH

All approved Project Jarvis specifications must be stored in Git.

Git provides the durable, version-controlled communication mechanism between specification work and implementation work.

Git initially carries:
- Specifications
- Design documents
- Implementation concerns
- Questions
- Proposals
- Decisions
- Discussion items
- Generated project documents
- Code and related project artifacts

No approved specification should exist only inside an AI conversation.

A specification becomes part of the project when it is committed to the appropriate Git repository.

4. COLLABORATION MODEL

The system initially involves three roles.

HUMAN
The human provides goals, requirements, business understanding, priorities, clarification, and final decision authority.

SPECIFICATION / ANALYSIS AI
The analysis AI works interactively with the human to understand requirements, examine implementation questions, reason about architecture, and produce specifications and design documents.

IMPLEMENTATION AI
The implementation AI builds the system. It has freedom to determine the best technical implementation consistent with the approved specification and existing architecture.

The implementation AI is also responsible for identifying problems in specifications rather than blindly implementing them.

These roles must be defined by responsibility rather than permanently tied to a particular AI vendor.

5. THE CURRENT PROBLEM

Today the human frequently acts as the communication bus between AI systems.

Implementation AI → displays concern → human reads concern → human takes screenshot or copies text → human sends it to analysis AI → discussion occurs → analysis AI produces document → human downloads document → human transfers document → implementation AI receives it.

This creates unnecessary hops.

The Gateway exists specifically to eliminate this workflow.

6. TARGET WORKFLOW

The human interacts with one interface.

The implementation AI can continue building concurrently.

The analysis AI and human can continue specification work concurrently.

Information flows between the two workflows through the Gateway and Git without requiring the human to manually transport it.

7. SINGLE EXTERNAL ENTRY POINT

The AI Communication Gateway must be the only externally exposed Jarvis service.

External clients must NOT connect directly to:
- Controller
- Agents
- Databases
- Internal APIs
- Model providers
- Git services
- Internal Jarvis processes

External devices connect only to the Gateway.

The Gateway then communicates with internal Jarvis services.

8. INITIAL CLIENT

Version 1 must support a phone-based web client.

The initial client may run in Safari or another suitable mobile browser.

A native mobile application is NOT required for the first implementation.

However, the Gateway API and transport architecture must not depend on the browser implementation.

9. VOICE-FIRST INTERFACE

Voice is a primary interface, not an optional enhancement.

The desired experience is similar to a natural continuous AI voice conversation.

The interface should eventually support:
- Natural speech
- Streaming responses
- Low latency
- Interruption
- User barge-in while AI is speaking
- Conversation continuity
- Visible transcript
- Text input when desired
- Document and artifact awareness
- Switching between voice and text without losing context

10. ONE-HOP REQUIREMENT

The user experience must be designed around one-hop interaction.

Example:

USER:
"Create the final specification and send it to the project."

That should be ONE interaction.

The Gateway should determine the required operations behind the scenes.

11. TRANSPORT ARCHITECTURE

Raw socket programming is not required for the initial implementation.

Preferred transport:
- HTTPS for normal API operations.
- WebSockets or an equivalent secure bidirectional streaming transport for real-time communication.

The transport layer must remain logically separated from higher-level Gateway behavior.

12. SECURITY

All external communication must be authenticated and encrypted.

At minimum:
- TLS / HTTPS
- Secure WebSockets where used
- Authentication
- Session management
- Request validation
- Authorization boundaries
- Appropriate rate limiting
- Secure credential handling
- Logging of security-relevant events

API keys and internal credentials must never be stored on the phone client.

13. CONTROLLER RELATIONSHIP

The phone does NOT connect directly to the Controller.

Architecture:

PHONE
↓
AI COMMUNICATION GATEWAY
↓
JARVIS INTERNAL INTERFACE
↓
CONTROLLER / SERVICES / AGENTS

The Controller remains an internal orchestration component.

14. GIT COMMUNICATION

For the initial implementation, Git is the primary artifact exchange mechanism between specification and implementation workflows.

Git communication is bidirectional:

IMPLEMENTATION → GIT → GATEWAY

and

GATEWAY → GIT → IMPLEMENTATION

The Gateway coordinates. Git preserves.

15. IMPLEMENTATION CONCERNS

The implementation AI must have a structured mechanism for reporting:
- Questions
- Specification ambiguities
- Architectural concerns
- Conflicts
- Suggested improvements
- Implementation discoveries
- Blockers
- Non-blocking observations

These must become durable project artifacts.

16. DISCUSSION QUEUE / SCOREBOARD

The Gateway must support a deferred discussion mechanism.

Working name:

PROJECT SCOREBOARD

The Scoreboard contains unresolved items requiring future human or analysis attention.

A Scoreboard item should eventually contain:
- Unique ID
- Creation time
- Source
- Related specification
- Related code/component
- Question or concern
- Importance
- Blocking/non-blocking status
- Current status
- Discussion
- Decision
- Resolution
- Related commits

The detailed Scoreboard schema will be defined in a later specification.

17. NON-BLOCKING DEVELOPMENT

Not every implementation question should interrupt development.

If the implementation AI encounters a non-critical question, it should record it and continue working where safe.

Blocking issues should be clearly identified.

18. CONTINUOUS SPECIFICATION FEEDBACK

The implementation AI is not simply a recipient of specifications. It is a source of architectural information.

SPECIFICATION → IMPLEMENTATION

must always have a corresponding feedback path:

IMPLEMENTATION → SPECIFICATION

19. SPECIFICATION APPROVAL

AI systems may propose specification changes.

They must not silently redefine approved architecture.

Significant architectural changes should follow:

PROPOSAL → DISCUSSION → HUMAN REVIEW → APPROVAL → SPEC UPDATE → GIT COMMIT → IMPLEMENTATION

20. DOCUMENT GENERATION

When the human and analysis AI complete a specification or design document, the Gateway should eventually be capable of publishing it directly to Git.

Target interaction:

Human:
"That's approved. Publish the specification."

The Gateway:
- Generates/finalizes the artifact.
- Determines its appropriate repository location.
- Writes it.
- Commits it.
- Makes it available to implementation.
- Reports completion to the user.

21. INITIAL PHASE

Phase 1 requires:
- Secure external Gateway
- Phone-accessible web interface
- Text conversation
- Initial voice conversation
- Authentication
- Connection to the selected analysis LLM
- Git reading
- Git writing
- Specification publishing
- Detection of implementation discussion items
- Basic Scoreboard
- Conversation/session continuity

22. DEVELOPMENT-TIME REQUIREMENT

Jarvis is being used to help build Jarvis.

Therefore, the communication infrastructure cannot initially depend on the entire future Jarvis architecture already existing.

The first Gateway implementation must be capable of running as a small independent service while the larger system is under construction.

23. FAILURE ISOLATION

The Gateway should remain usable when practical even if an internal development component is unavailable.

Failure of an implementation agent should not necessarily prevent:
- Voice conversation
- Specification work
- Reading existing Git artifacts
- Creating new design artifacts
- Reviewing the Scoreboard

24. MODEL INDEPENDENCE

The Gateway must not fundamentally be a "Claude Gateway" or "ChatGPT Gateway."

It is the AI COMMUNICATION GATEWAY.

Models are services behind it.

25. FUTURE DIRECT FILE TRANSFER

Git is the initial artifact transport.

Future versions may support direct file transfer between the phone, Gateway, Jarvis workspace, and AI systems.

This is not required to prove Version 1.

26. DESIGN PRINCIPLE

THE HUMAN SHOULD MAKE DECISIONS, NOT TRANSPORT MESSAGES.

The Gateway should automate mechanical coordination.

The human remains responsible for intent, judgment, priorities, and important approvals.

27. ULTIMATE VISION

The eventual experience should be extremely simple.

The user picks up a phone and starts talking.

Behind that conversation:
- One AI may be implementing.
- Another may be analyzing.
- Jarvis may be monitoring project state.
- Git may be changing.
- New implementation questions may be arriving.
- Specifications may be evolving.
- Agents may be executing work.
- Documents may be generated.
- Decisions may be waiting.

The user does not manually coordinate those systems.

The AI Communication Gateway does.
