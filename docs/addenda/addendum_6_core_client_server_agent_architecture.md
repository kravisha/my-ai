## Canonical process model, authority boundaries, lifecycle, health, scaling, dashboards, and memory

### 1. Process Topology

- Server: persistent backend host. Long-running concurrency and worker execution live in backend processes.
- Coordinator: internal server component. It is a factory manager and executor, not an autonomous policy maker.
- COO / Monitoring Agent: separately spawned privileged client process and autonomous operational authority for the agent ecosystem.
- Client: requests services and receives reports.
- Server dashboard: produced by the coordinator and shows server/process state.
- COO interface: shows operational health, workload, objectives, scaling decisions, alerts, and agent status.

### 2. Startup Sequence

1. Start the server.
2. Initialize the coordinator inside the server.
3. The coordinator spawns the COO privileged client as the first managed process.
4. The COO loads objectives, health policy, role definitions, shared watchlists, and organizational state.
5. The COO instructs the coordinator to spawn the baseline population.
6. Initial baseline is one instance of each required role unless a test specifies otherwise.
7. The COO assigns initial work and begins its continuous decision loop.

### 3. Authority Model

- The COO decides what to spawn, retire, restart, scale, or investigate.
- The coordinator executes COO directives and reports success/failure and process state.
- The coordinator must not independently invent scaling policy or agent strategy.
- Individual agents make decisions only within their role boundaries.
- A future Chief Intelligence Officer is a strategic synthesizer, distinct from COO operational control.

### 4. COO Objectives

- Maintain physical health: processes alive, resources available, queues functioning, dependencies reachable, no sustained resource crunch.
- Maintain ecosystem health: defined objectives are being met or showing expected progress.
- Prevent avoidable idleness while avoiding wasteful overscaling.
- Observe queue depth, throughput, latency, idle time, failure rates, resource use, and quality grades.
- Estimate sustainable capacity as the system matures and avoid exceeding it.
- Future objectives may include workload targets and financial-return quality; the first implementation stays conservative and measurable.

### 5. Initial Scaling Policy

- Normal baseline is one process of each role.
- If Analysis is idle for an extended configurable period, initially about one hour, the COO checks whether Explorer and Speculator are healthy and searching.
- If upstream discovery is healthy but starving Analysis, temporarily add discovery workers, for example two additional workers.
- When useful work begins flowing and the need ends, retire temporary workers and return toward baseline.
- If the Analysis queue grows faster than it is consumed, increase Analysis capacity.
- Scale producers when consumers are starved; scale consumers when queues are backing up.
- Log and grade every scaling decision and its observed effect.

### 6. Agent Health and Lifecycle

- Health indicators include accuracy drift, false positives, inconsistency, repeated failures, throughput degradation, resource growth, context/memory bloat, and validation performance.
- The COO may restart or refresh agents periodically or when health metrics justify it.
- A future refresh policy may use task count, runtime, resource growth, or measured performance; do not hard-code human-style fatigue assumptions.
- Agents may review performance and propose improvements, but production changes require validation.
- Recognition and performance records survive process restart.

### 7. Shared Server-Side Knowledge

- Maintain shared configuration and knowledge that agents can read and, under policy, improve.
- For social research, maintain a shared list of communities/sources. Seed it with Reddit and allow controlled expansion as useful sources are discovered.
- Source-list changes must be attributable, reversible, and gradable.

### 8. Conflict Rule

- Do not silently override an existing requirement when a new statement appears to conflict with it.
- If two requirements cannot both be true, stop implementation at that decision point and request clarification.
- After clarification, update the canonical specification so the implementation has one internally consistent rule.
- Do not preserve stale alternatives merely because they appeared in an older plan.
