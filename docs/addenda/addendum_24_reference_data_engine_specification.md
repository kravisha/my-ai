SPECIFICATION 01 — REFERENCE DATA ENGINE

Project Jarvis / My AI Status: Day Zero Foundational Specification

1. Purpose

The Reference Data Engine, also referred to as the Metadata Engine, is
the first foundational data engine of the system.

Its purpose is to create, validate, maintain, version, and serve the
canonical description of every tradable asset known to the organization.

The engine answers three fundamental questions:

1.  What kinds of assets exist?
2.  Which specific assets do we know about?
3.  How is each asset uniquely identified and related to the rest of the
    financial world?

No Explorer, Speculator, Analyst, market-data process, or strategy
process should invent its own security identity model.

The Reference Data Engine is the canonical source.

2. Position in Day Zero

The expected startup sequence is:

Bootstrap → Controller → COO → system readiness inspection → schema
initialization if required → Reference Data Engine → Reference Data
certification → selected mission data engine → operational agents

If usable reference data already exists, it is validated before reuse.

If required reference data is absent or insufficient, the COO starts the
Reference Data Engine automatically.

Dependent processes remain blocked until minimum reference-data
readiness has been certified.

3. Ownership

The COO is responsible for instantiating and supervising the Reference
Data Engine during startup.

The Reference Data Engine owns reference-data domain decisions.

The COO owns orchestration.

The Controller owns system-level lifecycle/orchestration authority.

The CEO remains strategic and constitutional and does not directly
operate this infrastructure engine.

4. Asset Universe

The system shall maintain three distinct concepts.

4.1 Asset Universe

The complete catalog of asset classes the organization is interested in
eventually understanding or supporting.

This is aspirational and extensible.

4.2 Capability Set

The subset of the Asset Universe the current software can actually
process correctly.

4.3 Current Focus

The subset currently selected for research, simulation, training,
testing, or operation.

These three registries are living metadata.

They may expand or contract over time.

5. Asset-Class Granularity

Asset classes shall be defined at the level at which operational
capability differs.

The system must not claim generic support for a broad category when it
can process only part of that category.

Examples may include:

-   stocks
-   stock options
-   ETFs
-   ETF options
-   futures
-   futures options
-   commodities
-   commodity options
-   currencies / FX
-   fixed income
-   digital assets
-   other classes added later

The catalog must support expansion without requiring architectural
redesign.

6. Canonical Asset Identity

Every known tradable instrument shall receive a stable internal
canonical asset ID.

This internal ID is the primary identity used throughout the
organization.

External identifiers are mappings around the canonical ID.

The system must not assume that CUSIP, ticker, ISIN, FIGI, or any other
external identifier exists for every asset.

7. Identifier Metadata

For every supported asset class, the engine shall maintain rules
describing:

-   applicable identifier types
-   required identifiers
-   optional identifiers
-   uniqueness rules
-   venue-specific identifiers
-   multiple identifiers per asset
-   identifier aliases
-   identifier history
-   mappings among external identifiers
-   canonical internal asset ID

Identifier architecture must be metadata-driven rather than hard-coded
into downstream agents.

8. Security / Instrument Master

The Reference Data Engine shall build and maintain the canonical
Security Master.

Where applicable, each instrument record should contain or resolve to:

-   canonical asset ID
-   asset class
-   symbol
-   security/instrument name
-   issuer
-   exchange or trading venue
-   currency
-   country/jurisdiction
-   active/inactive status
-   external identifiers
-   underlying instrument
-   derivative relationships
-   contract characteristics
-   listing information
-   source provenance
-   validation status
-   effective/version dates

The schema shall remain extensible.

9. Assets Table

The Assets table is the canonical work-discovery list used by downstream
agents.

At its simplest, it provides:

-   canonical asset ID
-   asset class
-   primary usable identifier
-   active/focus state

The Explorer can iterate over this table rather than discovering asset
identity independently.

The initial Assets table only needs sufficient coverage for Current
Focus.

Its long-term purpose is continuous expansion toward the broader Asset
Universe.

10. Additional Reference Masters

The engine should support canonical reference tables for:

-   issuers
-   exchanges
-   trading venues
-   currencies
-   countries/jurisdictions
-   trading calendars
-   holidays
-   identifier types
-   asset classes
-   asset relationships
-   corporate-action reference metadata
-   symbol history
-   source registry
-   provenance
-   validation results

11. Free/Public Bootstrap Sources

Day Zero should begin with legally usable free/public reference-data
sources where practical.

Potential source categories include:

-   SEC EDGAR and regulatory filings
-   official exchange symbol/security directories
-   OpenFIGI where permitted by its terms and limits
-   issuer disclosures
-   official/public trading calendars
-   public classification datasets
-   other validated free sources

Each external source shall be isolated behind an adapter.

The canonical model must not depend directly on any one vendor.

A source can therefore be added, removed, replaced, or upgraded without
redesigning downstream consumers.

All source licensing, attribution, redistribution restrictions, and rate
limits must be respected.

12. Ingestion Pipeline

Each source adapter should feed a common pipeline:

Acquire → Parse → Normalize → Validate → Resolve Identity → Reconcile →
Merge → Record Provenance → Publish

Source data must not silently overwrite canonical data.

Conflicts shall be resolved using explicit rules.

13. Source Authority and Confidence

Different sources may disagree.

The engine shall support:

-   source authority ranking
-   field-level provenance
-   confidence where useful
-   conflict detection
-   reconciliation rules
-   manual or agent-assisted review for unresolved conflicts

A disagreement is data, not something to hide.

14. Auditability

Material canonical values should be traceable to their origin where
practical.

Audit information should include:

-   source
-   retrieval timestamp
-   source record identifier
-   transformation/version
-   validation result
-   reconciliation decision
-   prior value when changed

Corrections should be versioned rather than silently erased.

15. Idempotency

The Reference Data Engine must be safe to run repeatedly.

Reprocessing unchanged input must not:

-   create duplicate instruments
-   create duplicate mappings
-   corrupt relationships
-   arbitrarily change canonical IDs

Startup and recovery must be deterministic.

16. Validation

Before declaring readiness, automated checks should include:

-   schema validity
-   required-field completeness
-   duplicate detection
-   canonical-ID uniqueness
-   identifier collision detection
-   invalid mappings
-   broken relationships
-   unsupported asset classes
-   source conflicts
-   malformed records
-   minimum Current Focus coverage

17. Readiness

Readiness does not mean that every tradable instrument on Earth has been
cataloged.

Readiness means that the Reference Data Engine satisfies the explicit
minimum requirements of the Current Focus and the mission that is about
to run.

The engine reports a structured readiness result to the COO.

18. COO Interaction

At startup, the COO asks:

1.  Does the required reference-data schema exist?
2.  Does usable reference data exist?
3.  Is it valid?
4.  Does it cover the Current Focus sufficiently?

If YES:

The COO accepts the readiness result and proceeds.

If NO:

The COO starts the Reference Data Engine.

The UI must visibly show that the Reference Data Engine has started and
display its progress.

When the engine becomes ready, it emits a readiness event.

The COO then proceeds to the next dependency.

19. User Interface Status

The system should expose Reference Data Engine progress to the
operations dashboard.

Example states:

-   NOT_STARTED
-   STARTING
-   INGESTING
-   NORMALIZING
-   RESOLVING_IDENTITIES
-   VALIDATING
-   RECONCILING
-   READY
-   DEGRADED
-   FAILED

Useful progress information may include:

-   sources processed
-   assets discovered
-   assets accepted
-   duplicates resolved
-   conflicts detected
-   identifiers mapped
-   Current Focus coverage
-   validation failures

The user should not need to inspect terminal output to understand
progress.

20. Stable Consumer Interface

Downstream consumers should use stable contracts such as:

-   get_asset(canonical_id)
-   resolve_identifier(identifier_type, value)
-   resolve_symbol(symbol, venue)
-   list_assets(asset_class)
-   list_focus_assets()
-   get_identifiers(canonical_id)
-   get_issuer(canonical_id)
-   get_exchange(venue_id)
-   get_trading_calendar(venue_id)
-   get_relationships(canonical_id)
-   get_provenance(canonical_id)
-   get_validation_status(canonical_id)

Exact implementation names may change, but the architectural contract
remains.

21. Failure Behavior

If minimum reference-data requirements cannot be satisfied:

-   the engine must not claim READY;
-   the COO must keep dependent processes blocked;
-   the failure must be visible on the dashboard;
-   diagnostics must identify the failed prerequisite;
-   retry must be possible;
-   successfully validated data should not be destroyed unnecessarily.

22. Testing Requirements

The engine implementation shall include automated:

-   unit tests
-   schema tests
-   adapter tests
-   parsing tests
-   normalization tests
-   identifier-resolution tests
-   duplicate tests
-   collision tests
-   reconciliation tests
-   database constraint tests
-   integration tests
-   restart/idempotency tests
-   failure/recovery tests
-   readiness-gate tests

User Acceptance Testing follows implementation and integration testing.

23. Initial Acceptance Criteria

Version 1 is acceptable when it can:

1.  Start against an empty supported database.
2.  Create or use the required schema.
3.  Load configured free/public reference sources.
4.  Normalize source records into the canonical model.
5.  Generate stable canonical asset IDs.
6.  Populate Asset Universe metadata.
7.  Populate Capability Set metadata.
8.  Populate Current Focus metadata.
9.  Populate a usable Security Master for Current Focus.
10. Populate the Assets table.
11. Resolve supported external identifiers consistently.
12. Prevent duplicate canonical instruments across reruns.
13. Record provenance.
14. Detect material conflicts.
15. Survive restart and rerun safely.
16. Fail closed when minimum requirements are not met.
17. Report progress to the UI.
18. Certify readiness to the COO.
19. Serve reference data through stable downstream interfaces.

24. Architectural Boundary

This engine owns reference/master data.

It does NOT own:

-   simulated market prices
-   historical price-series acquisition
-   live market feeds
-   volatility-surface construction
-   strategy logic
-   put-call parity analysis
-   speculation
-   investment analysis
-   evaluation/training outcomes

Those belong to separate engines and agents.

This boundary is intentional.

25. Foundational Principle

Reference data defines the world the organization knows exists.

Market data describes what happens to that world.

Agents reason about that world.

Therefore reference identity must exist before downstream intelligence
can operate reliably.
