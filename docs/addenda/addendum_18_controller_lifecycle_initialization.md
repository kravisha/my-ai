PROJECT JARVIS
LIFECYCLE-MANAGED CONTROLLER INITIALIZATION SPECIFICATION

Status: Proposed / Approved for implementation
Purpose: Eliminate import-time side effects and make Controller startup/shutdown explicit.

1. BACKGROUND

The current backend/main.py creates a Controller at module scope. As a result, merely importing
backend.main can construct the Controller, open the configured SQLite database, initialize schema,
run additive migrations, and seed metadata.

This creates an undesirable side effect: importing code can modify system state or touch a real
database even when the application itself has not intentionally started.

2. OBJECTIVE

Controller construction must be moved out of Python module import time and into the explicit
application/server lifecycle.

Core rule:

    IMPORTING CODE MUST NOT START JARVIS OR MODIFY PERSISTENT STATE.

The Controller should exist because the Jarvis server has started, not because some Python module
happened to be imported.

3. REQUIRED LIFECYCLE

A. MODULE IMPORT
   - backend.main may be imported safely.
   - No Controller is constructed.
   - No database connection is opened because of Controller construction.
   - No schema DDL or migrations are run.
   - No static metadata is seeded.
   - No agents or operational services are bootstrapped.

B. APPLICATION STARTUP
   - FastAPI lifespan/startup explicitly constructs exactly one Controller for that application
     instance.
   - Controller initialization may then initialize the database/schema and perform required
     migrations.
   - Existing bootstrap behavior, including controller.bootstrap_self() / bootstrap_coo() where
     appropriate, should occur under controlled application startup.
   - The initialized Controller becomes available to routes and services through an explicit
     application-owned accessor/dependency/state mechanism.

C. NORMAL OPERATION
   - Routes that currently reference the module-level controller must obtain the active lifecycle-
     managed Controller instead.
   - There should be one authoritative Controller instance for the running server lifecycle unless
     architecture explicitly requires otherwise.
   - No route should silently construct a replacement Controller.

D. APPLICATION SHUTDOWN
   - The application lifecycle owns cleanup.
   - controller.close() or the equivalent cleanup routine must execute during shutdown.
   - Database handles, loops, workers, and other Controller-owned resources must be released cleanly.

4. ROUTING / DEPENDENCY REQUIREMENT

Existing routes currently depending on the global `controller` reference must be migrated safely.

Preferred approaches:
   - FastAPI app.state
   - A FastAPI dependency/accessor that retrieves the lifecycle-owned Controller
   - Another explicit dependency-injection mechanism consistent with the existing architecture

Avoid replacing one hidden global with another hidden global.

5. DATABASE SAFETY REQUIREMENTS

The change must guarantee that:

   - Importing backend.main cannot create or migrate the database.
   - Tests can select/configure their database before Controller construction.
   - A developer's real financial_intelligence.db cannot be modified merely because a test,
     documentation generator, CLI utility, or script imports backend.main.
   - Existing schema and migration behavior remains functionally equivalent when the actual server
     starts.

6. TEST REQUIREMENTS

Update tests that assume `backend_main.controller` exists at import time.

At minimum test:

   1. Import safety:
      Import backend.main and verify Controller/database initialization has not occurred.

   2. Startup:
      Start the FastAPI application lifecycle and verify exactly one Controller is initialized.

   3. Database isolation:
      Point the test environment at a temporary/test database before application startup and verify
      the Controller uses it.

   4. Route access:
      Verify routes can access the active Controller after startup.

   5. Shutdown:
      Verify Controller cleanup/close occurs when the application lifecycle ends.

   6. Regression:
      Run the existing suite and ensure current Controller/COO/bootstrap behavior remains intact.

7. ACCEPTANCE CRITERIA

The implementation is accepted when all of the following are true:

   - `import backend.main` is side-effect-free with respect to Controller/database initialization.
   - Controller creation happens only during explicit application startup.
   - The application exposes the active Controller to routes without relying on construction at
     module import.
   - Existing server behavior is preserved after startup.
   - Tests no longer need import-time database-path redirection to protect the developer database.
   - Shutdown closes Controller-owned resources cleanly.
   - Existing tests pass, with tests updated where the old import-time behavior was intentionally
     asserted.

8. SCOPE CONTROL

This task is a lifecycle refactor, not a redesign of the Controller, COO, agent hierarchy, database
schema, or Jarvis governance model. Preserve existing behavior unless a change is strictly necessary
to remove the import-time dependency.

Do not introduce unnecessary abstractions or a new service framework solely for this fix.

9. IMPLEMENTATION REVIEW DIRECTIVE

Before implementation, critically review this proposal against the current repository.

Check:
   - whether the suggested lifecycle mechanism fits the existing FastAPI lifespan implementation;
   - whether any routes, tests, scripts, CLI tools, or background loops depend on the module-level
     Controller;
   - whether moving initialization changes bootstrap order;
   - whether shutdown ownership is already partially implemented;
   - whether there is a simpler implementation that achieves the same import-safety guarantee;
   - whether the change creates duplicate Controller instances or race conditions.

Do not accept this specification blindly if the current code proves an assumption wrong. Preserve
the objective, explain any necessary deviation, and choose the smallest safe implementation.

End the review with a clear disposition:
   APPROVE AS WRITTEN / APPROVE WITH MODIFICATIONS / REJECT AND PROPOSE ALTERNATIVE.

10. RELATIONSHIP TO THE VOICE RELAY / JARVIS INTERFACE

This lifecycle change is compatible with the Voice Relay Web App architecture. That design already
places the phone-facing interface behind the existing FastAPI backend and expects the backend to own
conversation state, model calls, relay/file operations, and related server resources.

The Voice Relay specification describes the phone connecting to the FastAPI backend, which then
calls Anthropic and can write generated files into Git. This Controller lifecycle refactor should
therefore be treated as backend infrastructure hygiene, not as a change to the Voice Relay's
user-facing purpose or topology.

END OF SPECIFICATION
