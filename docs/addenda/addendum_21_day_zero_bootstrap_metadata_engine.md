DAY ZERO BOOTSTRAP & METADATA ENGINE
Design Checkpoint — August 21, 2026

PURPOSE
Day Zero creates the minimum viable world required before operational agents begin work.

1. BOOTSTRAP AND CONTROLLER
- The Controller is the first operational component created at system startup.
- It inspects the system and determines what exists.
- If databases are empty, it invokes the schema generator.
- The Controller is the only component that needs awareness of lifecycle stage.
- Other agents receive appropriate data/services without needing to know whether the underlying world is simulated, historical, or live.
- The Controller does not wake the organization until prerequisites are satisfied.

2. LIFECYCLE
Pre-Alpha:
- Simulation is the operational world.

Alpha:
- Historical market data becomes the operational world.

Beta:
- Simulation, historical data, and live market data can all be used for observation, testing, comparison, recertification, and validation.

Live:
- Entered only after sufficient confidence and certification.

3. DAY ZERO REFERENCE DATA / METADATA ENGINE
Reference data is created before Explorers begin work.

Root metadata includes:
- Asset Universe: the intended universe of asset classes the organization may eventually understand.
- Capability Set: asset classes the system can currently process.
- Current Focus: asset classes currently being worked on.
These are living registries and may expand or contract.

Asset classes should be operationally explicit. Stocks, stock options, futures, futures options, commodities, commodity options, etc. may be represented distinctly when capabilities differ.

4. IDENTIFIER MODEL
Different asset classes require different identifiers.
Do not assume CUSIP or any single identifier applies universally.

Maintain metadata describing:
- asset class
- identifier type(s)
- required/optional status
- uniqueness rules
- mappings between identifiers

5. SECURITY / ASSET MASTER
The long-term purpose is a continuously expanding master of tradable instruments.

At minimum:
- canonical asset ID
- asset class
- applicable external identifiers
- reference-data relationships

The initial Assets table can remain deliberately simple: a canonical list of assets/identifiers that downstream Explorers can consume.

6. STARTUP ORDER
Bootstrap
→ Controller
→ inspect environment
→ schema generator if required
→ Metadata / Reference Data Engine
→ Asset Universe / capability / focus metadata
→ identifier schemas
→ Security Master / Assets
→ validate required data
→ initialize appropriate data world
→ wake operational agents

7. SIMULATION WORLD
In Pre-Alpha, the Simulation Engine knows it is generating a simulation.

It must be capable of producing sufficient synthetic inputs for the organization, including:
- market data
- volatility-related data
- news/noise
- chatter/social-style noise needed by the Speculator
- scenarios and outcomes needed for evaluation

The COO/controller-side orchestration asks whether usable market data exists. The Simulation Engine determines whether existing simulated data is fit for its purpose. Failed datasets are rejected/rebuilt with enough retained information for audit and diagnosis.

8. CORE PRINCIPLE
Agents should consume domain interfaces such as “market data,” not lifecycle concepts such as “simulation,” “alpha,” or “beta.” Lifecycle knowledge belongs at the orchestration layer.
